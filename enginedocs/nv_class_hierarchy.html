Architecture Notes

The Mojave Class Hierarchy

Given what the record types actually share and where they actually diverge, what should this codebase's Node hierarchy look like? Grounded in what's real today in project/gamebryo/*.gd — every class below is either already there, or marked proposed as a direct extension of that real chain.

Companion to the field-level Mojave Data Model reference — that one documents what each record is; this one is angled toward what class it should become.

01 One root, not two

GamebryoReference moves from StaticBody3D to Node3D. The original reasoning for StaticBody3D was sound as far as it went — "an inert body with no shape is harmless" — but it baked a physics-body assumption into the one class every subtype inherits from, including a future Actor branch that needs to move under AI, which a static body can't do. Node3D keeps the one thing every subclass genuinely needs (a transform — a Reference's whole job is representing something placed somewhere) and drops the one thing only some of them need (a physics body).

Wherever collision or movement is actually required, the subclass adds its own internal physics-body child node and hangs shapes off that — composition instead of inheritance for the physics part specifically. That's what unifies World Objects and Actors under one real root instead of two: both are just "GamebryoObject plus an internal body," they just add a different kind of body.

Real refactor, not a rename. mesh_resolver.gd's populate_collision_children() currently adds shapes as direct children of whatever node it's given — today that node already is the physics body via inheritance. game.gd's interact raycast currently assumes the ray's collider is the GamebryoReference it wants to call activate() on. Both need to retarget to "walk up from the physics-body child to its owning reference" once the body becomes a child instead of the root.

02 Scope: Dynamic objects, not every placement

Worth naming precisely, because "a Node3D per placement" sounds expensive at Mojave scale and isn't, in practice. The real dividing line is Dynamic vs. Static — not "interactive," not "registered/unregistered" (language earlier drafts of this doc used, which undersold the point):

Dynamic: can have a script, or can move (or both) — either capability means an object's state can diverge from the ESM per-instance at runtime, which a shared-RID batch can't represent. Static: neither — its state never differs from what the ESM already says, so a shared RID is not just cheaper but correct.

Static

Thousands of rocks, fence posts, and generic STAT set dressing per tile. Bypasses this whole hierarchy via DirectGeometryBatch — shared-RID MultiMesh entries with real per-placement PhysicsServer3D bodies for collision, but no Node identity and no way to ever run a script or move independently. This is permanently correct for these types, not a gap to close.

Dynamic

Doors, containers, activators, lights, terminals, talking-activators, movable statics, and (once built) actors. Dozens per tile, not thousands. Every one of these must resolve through a real GamebryoReference — not optionally, not gradually.

What is gradual is which Dynamic types actually have a registered Node class today. mesh_resolver.gd confirms any base_type with no registered factory "always routes through the RID path at runtime" in the exterior-streaming pipeline — the same path Static content uses. A Dynamic type sitting unregistered (Terminal, TalkingActivator) isn't merely missing behavior — it's currently structurally incapable of ever running a script or being activated outdoors, because it isn't becoming a Node at all.

Fixing that means registering in two places, not one: GamebryoObjectRegistry's String → Callable factory dictionary (the interior CellLoader.build() path), and the threaded resolve path's own separate, deliberately fixed dispatch list that WorldStreamer actually calls — construct_from_resolved()'s own doc comment explains why it doesn't consult the mutable registry: a register() call must never be able to inject a non-thread-safe factory into a worker thread. Miss the second one and a type works indoors, then silently stays RID-batched outdoors.

03 Items: a Node/Resource duality, not a plain leaf

Weapon/Armor/Ammo/Ingestible/Book/ MiscItem/Key/Note all have a Model, so they can sit under GamebryoVisual when dropped loose in the world — but they have a second life the rest of that branch never needs. Per GECK's own documentation, an Item's Reference stops existing the instant it's picked up into a container: its data is re-shaped into a plain inventory-entry dict instead. (This is also the source of the dropped-hotkey bug — the hotkey lived on a reference that no longer exists once the item is picked back up.)

Don't model ItemNode as just another leaf. It needs the same duality this codebase already applies to mesh data — a GamebryoVisual-based node for the in-world state, a plain Dictionary/Resource shape for the in-inventory state, with an explicit to_inventory_entry() conversion between them, mirroring how resolve_raw_geometry() → build_geometry_entries() already separates raw data from constructed Node for a different reason in this codebase.

04 What never becomes a Node

Rule of thumb: the only things in this data model that ever earn a Node are things with an actual place in 3D space and a reason to be individually interactive. Everything else is data — parsed once, cached, referenced by ID, never instantiated into the tree.

QUST, DIAL/INFO, FACT, SCPT, and every leveled list should never be a Node — not Node3D, not even plain Node. A quest's stage table, a faction's rank/relationship table, a dialogue tree, a script's logic: none of it has any use for scene-tree membership. No parent/child position to track, no _ready()/_process() to hook, no signals to route through the tree. At the scale a full playthrough's worth of quests, scripts, and dialogue responses actually reaches — thousands of records — giving any of them a Node buys nothing and costs real overhead for zero benefit. Same shape of waste DirectGeometryBatch exists to avoid for world geometry, just for data instead of meshes.

The correct Godot shape is Resource — RefCounted-based, cheap to hold by the thousands precisely because it's never in the scene tree — held in a lookup table keyed by form ID/editor ID, the same pattern GamebryoMeshResolver already uses for its _nif_cache/ _image_cache. A GamebryoActor doesn't own its Faction as a child Node; it holds a reference into that shared table. A Quest doesn't exist anywhere in the tree until something with a real placement points at it.

05 Cross-cutting fields → composition, not more classes

A few fields recur across branches that otherwise have nothing to do with each other — Door, Weapon, and NPC_ all have a destructible-object hook; nearly everything has a Quest Item checkbox. Forcing these into the inheritance chain would mean multiply-inheriting across branches Godot's single-inheritance model can't express, and shouldn't — modeled the same way this project already treats activate(): a duck-typed capability, checked at the call site, not a base class.
