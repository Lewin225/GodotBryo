Architecture Notes

Mojave Save Architecture

What Gamebryo/FNV actually saves, why it's organized the way it is, and what a Godot-native equivalent should keep versus deliberately not reproduce.

Fifth of five companion documents, alongside the Mojave Data Model, Class Hierarchy, Script Interpreter, and Build Plan.

Sourcing note

Read the architecture-level claims with real confidence; read exact field layouts as "probably roughly right," not gospel.

01 The core idea: a diff, not a snapshot

A Gamebryo save is not a copy of the world. The full Mojave — every rock, every NPC, every container's default loot — already exists, fully specified, in FalloutNV.esm and its DLC masters. The save file only records what's different from that baseline for whichever objects actually changed. An untouched filing cabinet in a cell you never visited isn't in your save at all — the engine re-derives it from the ESM every time that cell loads.

This is why Bethesda saves stay a manageable size despite the game world being enormous, and it's the load-bearing design constraint that shapes everything else about the format.

02 What's actually in one

Header          player name, level, location, playtime, screenshot thumbnail, engine version
Plugin list     every active ESM/ESP, in load order -- FormIDs are load-order-relative
Changeforms     FormID + change-type bitmask + only the changed category data -- the actual payload
Global data    quest stages, global variable values, per-script local variable values,
                player stats/perks/reputation, active temporary magic effects
Created forms  objects that never existed in any ESM, generated at runtime -- fully
                serialized, since there's no baseline to diff against
PieceWhy it exists
ChangeformsOne entry per Reference/Actor/Quest whose state diverged from its ESM baseline. A looted container's changeform records its new inventory; an unopened one has no entry and regenerates from the ESM's own item list on load.
Plugin listFormIDs only mean anything relative to a specific load order — a save can't resolve correctly against a different plugin set without this, which is also the source of the classic "missing master" load warning.
Created formsGet a fresh, save-only FormID (the FF-prefix convention) and are stored in full, since there's genuinely nothing in any ESM to diff against.

03 How loading reconciles it

At load time: parse the plugin list and validate it against the currently active data set (this is the actual mechanism behind "this save requires Dead Money" type warnings). Then, for every object the game actually needs: the ESM/DLC-master data supplies the baseline, and if a changeform exists for that FormID, its fields patch the baseline in place. Created forms are simply materialized fresh from their own fully-serialized record. Nothing is ever reconstructed by replaying a change log — each changeform is itself already the final state, not a delta-of-deltas.

04 Does needing real multi-master loading change this?

Partly, and it's worth being precise about which part. Rendering DLC content correctly at all — not just saves — already requires real load-order-relative FormID resolution: a later-loaded master can override a base-game record by reusing its FormID under a different origin index. That's unavoidable infrastructure regardless of whether a save system exists.

Changes as a result

Using real FormIDs as save keys stops being "extra work to avoid" — once multi-master resolution exists for DLC, it's the natural, already-available identity to key a save entry on. No reason to invent a second ID scheme.

What doesn't change

The delta idea is separate from FormID identity. Reproducing Bethesda's specific bit-packed change-flag categories and per-category blob layout is still not worth doing — that's a 2010-era space optimization for a binary format nobody needs byte-compatibility with.

05 Keep vs. drop for a Godot-native design

IdeaWhy
Delta/sparse storage — only save what changedKEEPSame reason it mattered for Bethesda: serializing every placed object's full state every save would be enormous and slow in Godot too.
FormID as the save keyKEEPFree once real multi-master resolution exists for DLC — no reason to duplicate identity schemes.
Recording the active plugin/DLC set in the save headerKEEPEnables the same "you're missing content this save needs" validation, essentially free given load-order tracking is already required.
Bit-packed change-flag categoriesDROPA binary-format space optimization; a Godot Dictionary's own sparse key presence already tells you what changed, no bitmask needed.
Byte-compatible .fos layoutDROPNo value in matching Bethesda's file format bit-for-bit — nothing reads this save but this project's own engine.
Per-category blob ordering / fixed offsetsDROPAn artifact of a hand-packed binary format; Godot's own serialization (typed Dictionary, Resource, JSON) doesn't need it.

06 A sketch, tied to the other four documents

Mapped onto what's already been designed: the "what changed" fields per object aren't abstract — they're exactly the fields the Class Hierarchy and Script Interpreter documents already identified as mutable state. 

SaveState (Resource)
  plugin_list: Array[String]          # active masters, in load order -- the validation-at-load piece
  player_data: Dictionary             # stats, perks, position, inventory
  changed_references: Dictionary      # FormID -> { position?, health?, inventory?, disabled?, ... }
                                       # only present for a GamebryoReference that actually diverged
  quest_states: Dictionary            # FormID -> { stage, local_vars }
                                       # the Quest Resource's own runtime state, from the Class Hierarchy doc
  script_locals: Dictionary           # FormID -> { var_name: value }
                                       # per-instance ExecutionContext state, from the Interpreter doc
  created_forms: Array[Dictionary]    # fully-serialized, runtime-only objects -- no baseline to diff against

An entry only exists in changed_references at all if something about that Reference actually diverged from its ESM baseline — sparse by construction, the same property the changeform system has, without needing its binary encoding. A GamebryoActor's own local script variables (the Calling-Reference Contract from the Build Plan doc) are exactly what script_locals persists per FormID; a Quest Resource's stage and variables are exactly what quest_states persists. Nothing here needs a new concept — it's the same object model already designed, with a save/load boundary drawn around whichever fields are actually mutable at runtime.
