● Read through the whole thing (esm_browser.gd, esm_record_loader.gd,
  esm_resource_factory.gd, plugin.gd). My honest take:

  The core idea is genuinely good. Rather than building a custom dock UI to
  browse/edit ESM records, it materializes empty placeholder files under
  res://esm_mount/<TYPE>/Name__EditorID_FormID.nvrecord so they show up as
  ordinary files in the FileSystem dock, then intercepts loading that extension
  through a custom ResourceFormatLoader that parses the type+FormID back out of
  the path and builds a real typed Resource (NpcRecord, RaceRecord, etc.) on
  demand from the live ESM via EsmResourceFactory. That gets you Godot's entire
  Inspector reflection UI — nested objects, arrays, proper field labels — for
  free, for a binary format Godot has no native concept of. The path is pure
  identity; the content is never serialized, always computed fresh from the real
  ESM reader, so there's no risk of the inspector view drifting from what the
  runtime actually loads. That's the right call for a dev tool.

  The caching (_load_typed keyed by type:form_id) is also correct in a subtle
  way: two NPCs sharing a RACE get the same cached RaceRecord instance, so the
  Inspector's object identity for shared sub-records is right, not a copy each
  time.

  Where I'd push back or want more, if this becomes more than a debugging aid:

  - 9,130 placeholder files already sitting under project/esm_mount/ (confirmed
    just now) for only NPC_/RACE/HAIR/EYES/ARMO/ARMA/FLST/WEAP from the base ESM
    alone. It's gitignored, so no repo bloat, but that's a lot of nodes for the
    editor's FileSystem dock/UID cache to carry every session — worth knowing
    this is the actual cost of "browse everything."
  - No unmount/refresh path. _mount_esm() only ever adds files that don't exist
    yet; the display name is baked into the filename. If a record's FULL name
    changes (different ESM version, xEdit edit), the old file just sits there
    with a stale name — nothing renames or prunes it.
  - _get_resource_type always returns "Resource", so every mounted record gets
    the same generic icon in the dock regardless of whether it's actually an
    NpcRecord or a WeaponRecord — a real fidelity gap for a browsing tool, easy
    to fix by returning the concrete type per path.
  - Base FalloutNV.esm only. _open_esm() only opens the base ESM
    (GameDataConfigScript.ESM_FILE); DLC-only NPCs/items/armor are unreachable
    through this browser even though EsmResourceFactory itself doesn't care
    which ESM it reads from.
  - Scope mismatch between the button and the factory: the "Mount ESM" UI only
    offers 8 types, but the factory already supports loading
    ALCH/AMMO/BOOK/CCRD/CMNY/KEYM/MISC/LVLI too — those are just never surfaced
    by the mount button.

  None of these are bugs — the thing works and the architecture is sound —
  they're the gaps I'd expect from "useful internal tool," not "polished
  feature." If this is meant to stay a personal debugging aid, I'd leave it
  as-is. If it's going to be something you reach for often, the icon typing and
  a DLC-aware mount are the two I'd prioritize.

● Given that the actual goal is "drag a weapon resource onto an inventory slot
  to eyeball it working," the mount-to-filesystem step is more machinery than
  the requirement needs — and it's the source of basically every concern I
  raised. Here's what I'd do differently.

  What the current design is actually buying you, mechanically: looking at
  InventoryComponent (gamebryo/inventory_component.gd:12-15), there's already a
  @export var editor_item_to_add: EsmRecordResource slot with an "Add Item To
  Inventory" tool button. The whole reason esm_mount/'s .nvrecord files need to
  exist is so something is sitting in the FileSystem dock you can physically
  drag into that slot. The mount step, the custom ResourceFormatLoader, the
  filename-encodes-identity scheme — none of that is about loading the item,
  it's entirely in service of having something draggable.

  Alternate design: make the browser dock itself the drag source, skip the 
  filesystem entirely.

  esm_browser.gd already has the good part — a searchable, filtered ItemList of
  records, backed by EsmResourceFactory which builds a live typed Resource
  (WeaponRecord, etc.) on demand. Godot's Inspector drop target for a
  Resource-typed @export field accepts two drag payload shapes: {"type": 
  "files", "files": [...]} (what dragging a FileSystem-dock file gives you
  today) or {"type": "resource", "resource": <object>} — a resource instance
  that's already in memory, no path required. Override _get_drag_data() on the
  dock's ItemList to build the record via the factory (same
  factory.load_record(type_tag, form_id) call already used by the loader) and
  return it as that second shape. Dragging a row straight onto
  editor_item_to_add then works with zero files ever touching disk.

  What that removes, concretely:
  - The entire esm_record_loader.gd / custom ResourceFormatLoader — no more
    startup class-registration race to defend against.
  - The .nvrecord file convention and the "Mount ESM" step — nothing to go stale
    when a record's name changes.
  - All 9,130 placeholder files currently sitting under project/esm_mount/.
  - The base-ESM-only and 8-type-only scope limits stop mattering as
    separately-tracked gaps — the dock already builds any type the factory
    supports; you'd just extend SupportedTypes/_open_esm() for DLC ESMs once, in
    one place, instead of also worrying about mount-time file generation.

  What you'd lose, and whether it matters here: you lose a path you can
  preload() or hardcode as an ext_resource reference from a script or .tscn
  outside of dragging. In practice that doesn't cost you anything for the stated
  use case — once you drag a resource onto an export slot, Godot serializes it
  as an embedded subresource in whatever scene/resource owns that field, so it
  still persists across editor restarts; you just can't find "that one weapon"
  again as a named file later. If you ever want a stable, nameable reference to
  a specific test item (e.g. a fixture scene you reuse across many test setups),
  that's the one case where a handful of hand-picked, deliberately-created
  .tres files (not a blanket mount-everything pass) would still earn their keep
  — but that's a much smaller, opt-in ask than materializing the whole ESM.

  If you want to go a step further later, the same live-record-from-factory
  approach also supports a plain "Pick Item…" picker dialog (an
  EditorInspectorPlugin adding a button next to any EsmRecordResource field)
  instead of drag — more clicks, no drag-and-drop coordination needed, same
  zero-filesystem-footprint approach underneath.

● That broadens the calculus, and it changes my answer. For "any ESM record
  usable in any Inspector slot, anywhere," the filesystem-mount approach
  actually earns something the drag-only design doesn't: once a record is a real
  res:// file, it shows up in Godot's own built-in resource picker — the
  searchable "Quick Load" dropdown you get from clicking any @export var x: 
  SomeResource field's icon, anywhere in the project, with the ESM browser dock
  closed. Drag-from-a-live-dock only works when that dock happens to be open
  next to the Inspector you're filling in. So the file-based approach isn't
  wasted machinery for the general goal the way it looked for the narrow "drag
  one weapon" case — it's buying real integration with Godot's own discovery UI.

  The problems I flagged earlier are still real, though, and they're
  specifically about how eagerly it materializes, not about materializing at
  all:

  What I'd change, given the broader goal:

  1. Materialize on demand, not all-at-once. Right now "Mount ESM" writes a
     placeholder for every record of 8 hardcoded types in one pass — that's the
     9,130 files sitting there. For a general-purpose "reference any ESM record
     from the Inspector" tool, you don't need most of those ever to exist as
     files; you need the one you're about to reference to exist. Replace the
     blanket "Mount ESM" button with a per-row "Reveal/Create Reference" action
     in the search results list — write that one .nvrecord file the first time
     something actually needs to point at it. The dock's search/filter
     (_refresh()) can keep working straight off reader.get_record_index() in
     memory, with no file ever created just to browse.
  2. Unify the type list with the factory instead of duplicating it.
     esm_browser.gd's SupportedTypes (NPC_, RACE, HAIR, EYES, ARMO, ARMA, FLST, 
     WEAP) and EsmResourceFactory.load_record()'s match (which also handles
     ALCH, AMMO, BOOK, CCRD, CMNY, KEYM, MISC, LVLI) are already two
     independently-maintained lists that disagree — LVLI is loadable but never
     mountable. That's a duplication bug, not a design choice; the dock should
     ask the factory what it supports rather than keeping its own copy.
  3. Fix _get_resource_type to return the real concrete class per type_tag
     (WeaponRecord, NpcRecord, ...) instead of hardcoded "Resource" — this is
     what makes the built-in picker's type filtering and icons actually useful,
     and it's the whole payoff of going through the filesystem in the first
     place.
  4. Keep the live drag-from-dock path as the fast lane (from the previous
     message) for the common case of "I have the browser open right now and want
     to drop this straight into a field" — it costs nothing extra to support
     both, and it's strictly better than the file path when you don't need
     permanence.
  5. DLC ESMs and rename-on-change are the two I'd still leave as known,
     acceptable limitations for now rather than solve up front — worth a comment
     in the code, not worth blocking on.

  Net effect: same end capability (search, pick, reference any ESM record
  anywhere), but the filesystem only ever holds what you actually chose to
  reference, instead of a standing mirror of the entire base ESM.

  the subset of types that also have a constructible scene — which is exactly
  the set already registered in GamebryoObjectRegistry._register_defaults()
  (DOOR, CONT, ACTI, FURN, WEAP, MISC, NPC_, CREA, etc. — that registry is
  already your source of truth for "this type has a scene form") — add a
  right-click context-menu entry ("Build Scene") on the FileSystem dock via
  EditorContextMenuPlugin (Godot 4.3+). It runs the record's type_tag/form_id
  through the same registry the runtime streamer uses, wraps the result in
  PackedScene.pack(root), and opens it in a new scene tab or saves it alongside
  for reuse. One file, one clear default, one discoverable secondary action —
  and the action only ever appears for types where it's meaningful, since you
  gate it on GamebryoObjectRegistry having a factory for that tag.

  2. Split into two mounts if you want both to be independently 
  double-click-able. A second extension (or subfolder) whose loader's _load()
  runs the object-registry build pipeline and returns a PackedScene directly, so
  double-clicking that file opens the scene editor the same way a .tscn does,
  while the original .nvrecord stays the data view. This gives you two real,
  independently-discoverable artifacts per record instead of one file with a
  hidden second mode — but it doubles the on-demand-materialize machinery from
  the previous message (two lazy-create actions instead of one) for types where
  both views are wanted.

  I'd start with (1): it's strictly less machinery, keeps "drag the data into a
  field" as the obvious default, and the context-menu action is naturally scoped

  often as the data form for the same records, that's the signal to graduate to

● No — it doesn't need a refactor of GamebryoMeshResolver/GamebryoObjectRegistry
  at all, and having just read build() and _finalize() closely, I'm confident
  of that. build(placement: Dictionary) never actually requires a real REFR — it
  only reads base_type, model, base_form_id, editor_id, and optionally
  position/rotation/scale/script_form_id off the dict, and every one of those
  reads is .get(key, default) with a sane default (origin position, identity
  rotation, scale 1.0, empty editor_id). model is already a plain resolved path
  string by the time it reaches build() — it's not derived from a REFR's own
  fields, it's whatever the caller put there.

  So a WeaponRecord/EsmRecordResource already carries everything a synthetic
  placement needs: record.form_id → base_form_id, record.record_type →
  base_type, record.editor_id → editor_id, and the model path (already extracted
  from MODL/MOD2/etc. by EsmResourceFactory._model_fields() when the record was
  built). "Build Scene" from a base record just needs a small adapter —
  placement_from_base_record(record) -> Dictionary — that packs those four or
  five fields into a dict with the transform fields omitted (so it lands at
  identity/origin), then hands that straight to the existing build(). No change
  to the registry's dispatch, no change to _finalize(), no change to the
  resolver's signature.

  The one real distinction worth naming out loud in that adapter's own doc
  comment: this produces a placement with no refr_form_id (there's no cell
  reference behind it — it's a base record, not an instance). Everything already
  treats that as valid — it falls back to "%s_%X" % [base_type, refr_form_id]
  naming, which for refr_form_id == 0 just reads a little oddly (e.g. WEAP_0),

● Confirmed directly from the primary source (fopdoc/FalloutNV/Records/REFR.md —
  the same xEdit doc family our own enginedocs/Data Types/*.txt files already
  cite). Full answer to both parts:

  It's a defined, closed list — but applied sparsely, on demand. REFR is a
  variable-length sequence of optional subrecord chunks, not a fixed
  always-present struct. The relevant ones:

  XCNT | Count           | int32
  XHLP | Health          | float32   (this is condition/durability)
  XCHG | Charge          | float32
  XOWN | Owner           | formid    (ownership data)
  XRNK | Faction Rank    | int32     (ownership data)
  XAMT | Ammo Type       | formid
  XAMC | Ammo Count      | int32

  None of these carry a "always present" marker — every row in that table is a
  subrecord that's only written when it applies. A pristine, unowned,
  default-count item's REFR is essentially just NAME (the base FormID) and
  almost nothing else. XHLP only shows up once the weapon's health has actually
  diverged from the base record's default; XOWN only shows up once something is
  actually owned. This is exactly the "-1 = untouched" behavior OpenMW's
  CellRef.mChargeInt comment described — confirmed now from the real wire format
  rather than from OpenMW's C++ re-implementation of it.

  So the honest framing: the vocabulary is fixed and small (a known, finite set
  of override types — condition, charge, count, ownership, ammo-in-weapon — not
  an arbitrary schema-less bag) but each one is optional per-instance, attached
  only when that instance actually diverges from its base record. It's not
  "track any variable on demand" in the sense of arbitrary dynamic properties;
  it's "here's a known short list, and each one is skipped unless it's actually
  needed."

  For InventoryEntryResource, that argues against a generic Dictionary 
  extra-data bag. Godot Resources are well-suited to the same shape the real
  format actually has: a small number of explicitly named @export fields, each
  defaulting to a sentinel that means "not diverged" — condition: float = -1.0,
  and later owner_form_id: int = 0, ammo_type_form_id: int = 0 if/when
  weapon-loaded-ammo tracking becomes relevant. That's more idiomatic for a
  Resource (typed, inspectable, no stringly-keyed lookup) than mimicking the
  sparse-subrecord storage mechanism, while still matching its actual semantics
  — you just don't bother writing/touching condition for the 95% of items that
  are never fired or damaged, same as the real format never writes XHLP for
  them.

  This is the real Bethesda scheme: the top byte is which load-order file 
  authored this, the bottom three bytes are this object's index within that 
  file. A RefNum isn't a free-floating unique token — it's a claim of the form
  "object #N, as declared by file X." That claim is only meaningful while it's
  still describing something file X actually placed. The moment an item is
  carried out of its original cell and dropped into a completely different one,

  hasn't always been reliable. So the complaints you're recalling aren't a myth

  here" in the first place.

  re-parsing that record's full subrecord list on every single .damage or
  .model_path read, from every WeaponReference that happens to point at it.

  of cache is clearly earning its keep here — that part isn't in question.

  Where you're actually right to press: does the cached thing need to be a typed
  Resource subclass, or would a cached Dictionary (still cached, still 
  paid-for-once) be enough, at lower cost than a Resource? And I have to be
  honest — the document's "Resources have a higher cost than the C++ objects
  they replace" line was written specifically about the Reference side, arguing
  against one wide struct carrying fields most instances never use. Reusing that
  same sentence to also justify EsmBase's existence is sloppy — EsmBase doesn't
  replace a C++ struct at all, it replaces a raw Dictionary the native layer
  already hands back. That's a different comparison, and I shouldn't have let
  the wording blur the two together.

  honest answer is: it's not primarily about performance (both are O(1) after
  the first parse, both avoid re-hitting the native layer). It's the same three
  reasons the document already gives for why Reference needs per-kind subclasses
  instead of one generic bag, applied symmetrically to Base:

  - Editor tooling — InventoryComponent.editor_item_to_add: EsmRecordResource
    (inventory_component.gd:12) already relies on drag-and-drop,
    type-constrained Inspector fields. A cached Dictionary can't be dragged into
    an @export slot or type-constrained at all.
  - Static typing — entry.item_record is ArmorRecord (used throughout
    npc_actor.gd), Array[ArmorRecord] on EquipmentState — these need real class
    instances. A Dictionary-based cache would mean going back to if 
    raw.get("record_type") == "ARMO" string comparisons everywhere, exactly the
    ad hoc pattern already flagged as the thing to move away from
    (object_registry.gd's result["emittance_color"]).
  - Consistency — if duck-typed dictionaries were actually fine here, the whole
    case for per-kind Reference subclasses over one generic bag would also not
    hold, since it's the identical argument. Keeping Base as raw dictionaries

● Good question, and yes — GDExtension C++ absolutely can construct and return
  real Resource objects, not just Dictionarys. But there's a real wrinkle
  depending on how far you take it, and it lands differently depending on which
  of two versions you mean.

  Version 1: native code caches the raw parsed Dictionary (skip re-parsing bytes
  on repeat calls), GDScript still builds the typed Resource from it, same as 
  today. This is a clean, incremental win if profiling ever shows it's needed —
  the native layer currently reparses every subrecord from bytes on every single
  get_record_data() call (confirmed, no cache at all in
  esm_reader_gd.cpp:564-588), so caching that step in C++ would speed up repeat
  lookups without touching anything about where WeaponBase/ArmorBase are defined
  or how they're built. Doesn't lose inspector visibility at all — GDScript
  still constructs the real Resource, same as now.

  Version 2: native code owns the whole cache and constructs the actual 
  WeaponBase/ArmorBase instances itself, handing back real typed Resources. This
  is where your inspector-visibility instinct is right, but the reason is more
  specific than "we lose it" — it's conditional on how the Base classes get
  defined:

  - If WeaponBase etc. stay defined in GDScript (class_name WeaponBase extends 
    EsmBase), C++ constructing an instance of them means going through Godot's
    generic scripting/reflection API (ClassDB.instantiate("WeaponBase") or
    similar) rather than a direct C++ constructor call — native code doesn't
    have compile-time knowledge of a class GDScript defined. That's real
    overhead, likely eating most of the perf win you'd be reaching for in the
    first place, so it's not obviously better than Version 1.
  - If WeaponBase etc. get redefined as native GDExtension classes instead (real
    C++ classes, registered via ClassDB::bind_method), then yes — native code
    can construct and return them directly, full inspector visibility retained,
    genuinely fast. But that's a much bigger commitment: record field
    definitions move out of GDScript and into compiled C++, which directly
    undercuts something you specifically wanted to preserve two messages ago —
    not having to touch the native parser every time a new object or field gets
    added. Every new Base field would go back to being a native code change +
    recompile, not a GDScript edit.

  So the honest weigh-up: Version 1 is a safe, small win if the current
  per-form_id-once GDScript-side cache (esm_resource_factory.gd's _cache) turns
  out to actually be a bottleneck at scale — worth checking with real profiling
  before doing it, not assuming. Version 2's "real" form (native-defined Base
  classes) buys real speed but trades away the exact flexibility you already
  said you wanted to keep, so I wouldn't reach for it unless Version 1 turns out
  to be insufficient. I haven't profiled either — this is a live trade-off to
  keep in mind, not something to commit to without evidence either way.

❯ And those cached returned ESMBase records are pointers right? We're not

● Yes — confirmed by both Godot's own object model and what the code actually
  does.

  Resource in Godot extends RefCounted. Any GDScript variable holding a Resource
  (var x := some_resource) is a reference to that one heap object with its
  refcount bumped, never a copy — copying only happens if you explicitly call
  .duplicate(), which nothing in esm_resource_factory.gd does. So:

  gdscript
  if _cache.has(key):
      return _cache[key]     # same object, refcount++, not a copy
  ...
  _cache[key] = result       # the one object this key will ever produce
  return result

  Every WeaponReference whose base_form_id resolves to the same WeaponBase
  FormID ends up with _base pointing at the literal same object in memory. Ten
  pistols in your inventory means ten WeaponReferences and one shared WeaponBase
  between all of them — not ten copies of damage/model_path/etc. That's the
  whole mechanism that made the "does firing degrade every pistol at once" worry
  from a few messages back a non-issue: condition lives on each WeaponReference
  individually; model_path lives once, shared, on the object all ten point at.

  One thing worth stating as a requirement rather than an accident, for whenever
  this gets implemented (and relevant to last message's native-cache options
  too): this sharing only holds because the cache returns the existing reference
  on a hit rather than reconstructing. That's easy to get right in GDScript

● Genuinely easier than it might sound, and specifically because of the design
  choice already made, not despite it — worth spelling out why.

  What stays stable across the migration is exactly what consumers actually 
  touch. weapon.damage, entry.item_record is ArmorRecord, Array[ArmorRecord],
  drag-and-drop into an @export slot — all of that is Godot's property/class
  system, and it works identically whether a class was registered from GDScript
  (class_name WeaponBase extends EsmBase) or from native GDExtension code
  (GDREGISTER_CLASS(WeaponBase) with bound properties). This project already
  proves that daily — EsmReader, NifReader, WorldStreamer are all native classes
  consumed from GDScript with ordinary .method()/.property syntax, no special
  handling. So if WeaponBase moves to C++ and exposes the same property names,
  every existing .damage read and every is ArmorBase check keeps working with
  zero changes at the call sites.

  One thing worth correcting from a couple messages ago, since it matters here:
  I want to be precise that native-defined Resource classes don't lose Inspector
  support — plenty of Godot's own built-in types (StandardMaterial3D, etc.) are
  native and fully Inspector-editable. The tooling concern I raised was
  specifically about native code using reflection to construct instances of a
  class GDScript defined (ClassDB.instantiate("WeaponBase") reaching into
  someone else's script) — that's the awkward, slow path. A WeaponBase that's
  properly registered from C++ as its own real class has completely normal
  Inspector behavior. So this migration doesn't cost you visibility at all if
  done as a real native class, not a reflection hack.

  What actually costs effort is the byte-decode logic, not the class shape —
  esm_resource_factory.gd's _u32()/_string()-style subrecord parsing and the
  per-type builder functions (_build_npc, _build_alchemy, etc.) would need
  reimplementing in C++. That's real, proportional-to-how-much-exists-by-then
  work, but it's not novel risk — it's the same kind of port this codebase has
  already done elsewhere (nif_loader.cpp, esm_reader_gd.cpp already do exactly
  this class of byte-decode-into-typed-fields work natively). Known shape,
  bounded cost, nothing exotic about it.

  It doesn't have to happen all at once, either. Godot's object model
  interoperates transparently between native and GDScript-registered classes — a
  WeaponBase implemented natively can sit right next to a still-GDScript
  ArmorBase and cross-reference it fine. So this could go type-by-type (probably
  leaves first — HairRecord/EyesRecord before NpcRecord, which references them)
  rather than requiring a single big-bang cutover.

  One concrete real cost worth flagging, not hypothetical — I saw it directly 
  earlier this session: player.tscn bakes some of these as SubResource blocks
  referencing a GDScript script path (script = ExtResource(...)). A class moving
  from GDScript-defined to native-registered changes how it's referenced in
  serialized .tscn/.tres data (script-path reference vs. registered-class-name
  reference) — any already-baked scene data holding one of these would need a
  one-time re-save when its type migrates. Small, mechanical, but real, and
  worth remembering it exists rather than discovering it as a surprise later.

  So: keying the cache and the class definitions on the GDScript side now
  doesn't paint us into a corner — it's specifically the choice that keeps a
  future native migration cheap, because the property-based interface (not the
  implementation language) is what everything above the factory actually depends
  on.
