# Terrain streaming plan 1.3 — review feedback

Reviewed against `1.3-plan.html`, current master, the vendored Terrain3D
source, and Godot's thread/physics documentation on 2026-08-26.

## Verdict

This is a serious improvement. The plan now names the terrain owner, service
ownership, transition sequence, readiness result, queue mechanics, and a
credible route to remove the current per-pixel GDScript import cost. The
preferred Phase 2 direction is correct: worker-staged maps followed by a small
native batch-publish API.

**Phase 0 can start. Phase 1 should wait for the Phase 0 decisions already
listed. Phase 2 must not start until the three blockers below are resolved.**
They are consequences of the staged-region design, not objections to it.

## Blocking corrections

### 1. Final N=7 texture-ID maps cannot be built before slot assignment

Phase 2 says a worker creates all eight final map Images, but its
main-thread publication step then resolves staged LTEX FormIDs through the
active world's slot table. Those operations are ordered backwards: the
`TEX_ID_A/B` pixels need the final 1..127 LTEX slot values before they can be
encoded. A 32-bit FormID cannot simply be stored temporarily in the RGBA8
Terrain3D ID maps.

Pick one explicit design:

1. **Preferred:** prewarm and freeze a stable, per-world `LTEX FormID → logical
   terrain slot` map before any workers start. Hand workers an immutable
   snapshot, so they can construct final ID Images off-thread. The main thread
   separately ensures the corresponding render assets/LUT are available before
   publishing that batch.
2. Workers emit a compact local layer palette plus IDs/weights using local
   indices, and the native batch publisher remaps every pixel on the main
   thread. This preserves correctness but gives back much of the very work the
   staged design is intended to remove.

The plan already requires a deterministic prewarm decision in Phase 0; make
this dependency explicit and test that worker slot snapshots stay valid across
pause, cancellation, and worldspace changes.

### 2. “One complete 256×256 staged region” has an unstated latency policy

One LAND cell supplies a 33×33 vertex patch. A Terrain3D region is 256×256,
so one staged region spans many cells, and a cell can touch two regions at a
region boundary. Current `terrain3d_bridge.gd` deliberately uses per-pixel
writes because Terrain3D's bulk import replaces an entire region map; replacing
with a partially-filled image would erase previously imported neighbour data.

The plan needs to specify one of these policies:

- schedule and prepare every contributing cell for a region before first
  publication; or
- maintain an off-thread, per-region canonical staging buffer and publish
  immutable snapshots incrementally as cells finish.

For the second option, define snapshot copying/versioning, cell-to-region fan
out, default/unfilled samples, and the bounded publication cadence. For the
first, define the near-spawn ordering/readiness consequence: terrain must not
wait for arbitrary far cells in the same 256 region. Neither policy is free,
but leaving it implicit recreates the wholesale-region wipe that the current
bridge comment documents.

### 3. Fix the acceptance test that contradicts the chosen worker design

The test list says worker results must be “incapable of mutating any Godot
resource directly.” Phase 2 deliberately has workers construct new,
worker-owned `Image` resources. Both cannot be true.

Replace it with: workers must never read or mutate an **active/shared**
Terrain3D resource, region, asset, texture, or scene node; they may construct
and exclusively own detached Images/staging resources until a one-way publish
handoff. The stress test must prove that exclusivity, not prohibit the design
itself.

## PhysicsServer setting — justified, but phrase it correctly

The project does not set `physics/3d/run_on_separate_thread`, whose default is
`false`; the current PhysicsServer3D therefore runs on the main thread. It is
correct for Phase 2 to treat Terrain3D collision publication as main-thread
work under this configuration.

Do **not** describe that as a permanent requirement that physics must run on
the main thread. State it as a deliberate Phase 2 constraint:

> Phase 2 retains the default `physics/3d/run_on_separate_thread = false`.
> Terrain collision publication remains on the main thread in this phase. A
> later separate-physics evaluation is independent work; enabling the setting
> alone does not make Terrain3D's live collision update worker-safe.

This distinction matters because `Terrain3DCollision::update()` reads live
Terrain3D state and changes collision shapes; the current implementation has
no synchronisation around that wrapper. Godot documents that separate physics
can make the server thread-safe, but also restricts API access to physics
processing. It is not a free permission for a `WorkerThreadPool` job to call
the Terrain3D collision manager. [Godot ProjectSettings](https://docs.godotengine.org/en/stable/classes/class_projectsettings.html)

## Required clarifications before implementation

### Configure shared services before either streamer activates

The selected `Game`-owned shared ESM/resolver pair is the right choice, but
the construction contract is incomplete. Child `_ready()` methods run before
the parent `Game._ready()`. Do not move service creation to `Game._ready()`
and let either streamer consume it from its own `_ready()`. Define an explicit
`configure(esm, resolver, ...)` call before either `activate()`, or a dedicated
Game-owned service node initialized before both streamers. Include registry,
builder, and resolver-pool construction in that hand-off—not only the two
fields named in the text.

### Finish the half-open edge rule before writing the composer

The plan correctly admits the rule is still missing. It remains a real gate:
write the exact west/east and north/south skipped sample rows/columns, corner
owner, and the grid-axis inversion relationship before implementing the
composer. The code currently flips LAND rows and maps grid Y to negative world
Z; a casually written “lower y wins” rule is not enough to guarantee the same
physical border is chosen.

### Make inactive-world processing an explicit Phase 4 operation

Hiding Terrain3D and disabling collision does not automatically prove that
its physics processing is stopped. Phase 1 rightly adds explicit pause/resume
processing. Phase 4 must apply the same processing disable/enable sequence to
outgoing/incoming registry entries, including the direct
`set_physics_process(true)` resume required by Terrain3D's same-camera
behaviour. Add that to the Phase 4 switch steps and test it with camera motion
after returning.

### Clean up the document's remaining stale wording/markup

The Phase 0 audit still says various operations are “all confirmed
main-thread-only.” For active Terrain3D state that is the current design
constraint; for every detached resource operation it is too broad. Use the
active/shared wording consistently. Also remove the duplicate closing
`</section>` immediately before the acceptance-test section.

## Further assumptions that still need explicit proof

These are not reasons to reject the direction. They are hypotheses currently
embedded in it and should become Phase 0/2 measurements or prototype gates.

### Batch publication may still have an O(all resident regions) growth cost

`Terrain3DData::update_maps()` must recreate every generated map array when a
new region expands the region index. It is not just an upload of the new layer.
Further, `Terrain3D` connects `region_map_changed` to
`Terrain3DCollision::build()`, so changing region membership can also trigger
collision rebuild work. Publishing once per bounded batch is better than once
per cell, but it does not prove whole-world growth is frame-safe.

Make the native batch-publish prototype measure separately:

- edits to existing published regions (incremental texture-layer updates);
- adding one or several new regions (full generated-array rebuild);
- the signal-driven collision rebuild; and
- the cost at early, middle, and near-full world residency.

If region-array growth fails the frame budget, the next design must be stated:
larger/coalesced batches, reserved/preallocated array capacity, or a
double-buffered generated-array implementation. Do not discover this after the
global queue exists.

### Preferred capacity policy: spend VRAM to remove array-growth churn

For this project, make the intended answer explicit rather than treating it as
a fallback: after Phase 0's census, preallocate each worldspace's eight
generated GPU map arrays for its complete finite region domain, with stable
region-coordinate → texture-layer IDs. Initialise unused layers to the normal
empty/default maps, then update a layer in place when its staged region is
published.

For the Wasteland's likely 18×18 domain this is roughly 648 MiB of raw map
array VRAM, plus mipmaps/driver overhead and a comparable CPU image store.
That is an acceptable trade in the stated no-eviction, modern-hardware scope:
it replaces recurring full-array reallocations/uploads with bounded per-region
uploads and gives the queue stable IDs. It must remain census-driven per
worldspace rather than hard-coded to 324 layers, and the Phase 0 benchmark
must measure the actual resulting VRAM and publish cost.

### Detached `Image` construction is supported in principle, not yet proven here

Godot supports worker-side manipulation of an exclusively-owned resource before
handoff, but the proposed path uses many GDScript worker jobs, Image creation,
and a GDExtension batch publisher together. That exact combination has not
been tested in this project. The Phase 2 stress test must verify it under
rendering, physics queries, cancellation, and repeated reuse—not merely rely
on generic documentation.

### The shared resolver-cache benefit is an intended outcome, not a fact yet

The selected Game-owned resolver model should preserve shared DDS decodes
between TerrainStreamer worldspaces, but it is a future wiring change. Its
cache lifetime, initialization order, and hit rate must be measured after the
extraction. Until then, “decoded once” is a design target, not evidence.

### Separate physics is neither required nor automatically useful

The default main-thread physics setting is a valid Phase 2 constraint, but
there is no proof that enabling separate physics would improve this workload.
It could instead introduce main/physics synchronization in the first-person
controller and still leave Terrain3D's live data race unsolved. Treat any
separate-physics experiment as a separate benchmarked issue, not an unstated
future optimisation.

## Bottom line

Keep the worker-staged-region plus native batch-publication plan. It is the
right route to get meaningful import work off the main thread without racing
live Terrain3D data. First make slot assignment available to workers,
formalise partial-region publication, correct the contradictory acceptance
test, and record the PhysicsServer setting as a Phase 2 choice rather than an
immutable engine rule. Then Phase 2 is implementable.
