# Terrain Streaming Plan 1.0 — Implementation Feedback

## Verdict

**Do not start implementation from this plan unchanged.** The overall direction
is correct: terrain must have one owner, must be independent of object-cell
streaming, and must persist per worldspace. However, the current plan contains
two false architectural assumptions, an unsafe threading conclusion, and
missing contracts at the points where the new system meets rendering, physics,
and exterior transitions.

This feedback treats `1.0-plan.html` as superseding issue #19 where the two
conflict. In particular, a single outward-growing terrain residency set with
two import speeds, full N=7 import, and grass retained in the unified terrain
path are accepted scope decisions. The issue should link to this plan so its
older height-only wording does not mislead future work.

## Blocking corrections

### 1. One `Terrain3DTexturePool` cannot serve multiple Terrain3D instances

The plan says WastelandNV and Freeside Terrain3D nodes can share one
`Terrain3DTexturePool`, making only heightmaps per-worldspace. That is false
in the current implementation.

`Terrain3DTexturePool` stores a single `_terrain` and writes each asset through
`_terrain.assets.set_texture()`. Its slot table is therefore bound to one
specific Terrain3D instance. A second Terrain3D would not receive those assets,
while its bridge would still emit texture IDs and bind a separate material LUT.
See `project/gamebryo/terrain3d_texture_pool.gd`.

Choose and document one design before Phase 1:

1. **Simple, correct first pass:** one texture pool and one bridge per
   Terrain3D/worldspace.
2. **Shared logical catalogue:** cache normalized source images and a stable
   LTEX-to-logical-slot mapping once, then populate an independent Terrain3D
   asset pool in exactly that order for each worldspace.

The second option is not a small refactor. It must account for each terrain's
native material RID and its `_ltex_to_render_slot` parameter as well as its
asset list. Do not describe the memory as heightmap-only either way.

### 2. Workers must not mutate live Terrain3D data

The plan correctly notices that `Terrain3DData::set_pixel()` itself contains no
immediate RenderingServer call. Its conclusion is still unsafe. The method
mutates an `Image` owned by an active `Terrain3DRegion` and changes region
state. Terrain3D, the renderer, collision, and the main thread can all observe
that mutable live state. A per-region worker claim prevents two worker writes;
it does not make concurrent mutation of a live Godot Resource safe.

Workers may perform only detached preparation:

- ESM LAND lookup/decompression through a private `EsmReader`;
- coordinate conversion;
- decoded heights, normals, VCLR, VTXT opacity, and LTEX FormIDs;
- prepared arrays keyed by real LTEX FormID, not final render-slot ID.

All Terrain3D/Resource mutation remains main-thread-only until a dedicated
thread-safety test proves a narrower safe boundary. That includes
`Terrain3D`, `Terrain3DData`, `Terrain3DRegion`, `Image`, `Texture2D`,
`Terrain3DAssets`, and `RenderingServer`.

The main-thread commit resolves the prepared LTEX FormIDs to this Terrain3D's
slot table, creates any needed regions/assets, writes the prepared data, and
updates maps/collision state.

### 3. The map/upload cost is understated

The plan describes three generated Terrain3D map arrays. This fork has eight:
height, control, colour, TEX_ID_A, TEX_ID_B, WEIGHT_A, WEIGHT_B, and normal.
`Terrain3DData::update_maps(TYPE_MAX, false, false)` updates every edited map
layer; a full rebuild recreates all arrays. See
`native/terrain3d/src/terrain_3d_data.cpp`.

The Phase 0 benchmark must separately measure:

- LAND read/decode/preparation;
- main-thread region creation;
- main-thread texture/asset resolution;
- per-cell map writes;
- incremental upload;
- full array rebuild when a new region is introduced;
- collision update, if enabled;
- worst, p95, and average frame cost.

Without a concrete commit budget, "off-main-thread preparation" is a slogan.
The present bridge performs thousands of GDScript-to-GDExtension pixel calls
per cell; preparation alone may not move the real bottleneck.

## Missing contracts

### LAND enumeration and termination

There is no current worldspace LAND index. `EsmReader` can locate an exterior
CELL by grid through the ESM block/sub-block structure, then `get_land_data()`
finds that CELL's LAND child. It cannot currently enumerate `{ grid, CELL,
LAND }` directly.

Phase 0 must choose one finite source of truth for the queue:

- add a native worldspace LAND enumeration/index; or
- use the surveyed finite grid bounds and the existing indexed CELL lookup.

An unbounded spiral plus a no-cell cache is not a termination policy. The
coverage census must produce the exact queue domain, present-LAND count, and
missing coordinates per worldspace.

### Shared cell borders

Adjacent LAND cells write duplicate edge vertices. A region lock prevents a
data race but does not prevent nondeterministic last-writer-wins values when
worker completion order changes.

Define a canonical edge ownership rule, or first prove the real height, normal,
colour, IDs, and weights agree exactly at every shared edge and still commit in
a deterministic order. Add a regression test for it. Existing adjacent-cell
placement testing is not a whole-world scheduler contract.

### Player release readiness

"The requested coordinate landed" is insufficient. The transition contract
must define the exact spawn-safe terrain set and state:

- which cell/neighbourhood must have committed height data;
- whether Terrain3D collision must be built and enabled before release;
- whether GPU upload completion is required;
- cancellation behaviour if the player changes worldspace mid-load.

`game.gd` currently awaits only `WorldStreamer.streaming_settled`. This is a
required integration change, not an optional signal addition.

### Pause, worldspace switch, and cancellation

The plan covers WastelandNV → Freeside but not the normal exterior → interior
path. TerrainStreamer needs its own pause/resume lifecycle: hide its Terrain3D,
disable collision, stop or suspend its background queue, and reject stale
prepared payloads by generation/worldspace ID. Returning to an exterior must
restore the retained terrain instance safely.

`WorldStreamer.set_paused()` currently owns Terrain3D visibility and collision.
Those calls must move, not become duplicated responsibilities.

## Required Phase 0 additions

### Validate Terrain3D horizon coverage

Loading all LAND does not prove distant mountains render. Terrain3D has finite
clipmap settings (`mesh_lods`, `mesh_size`, and vertex spacing); current native
defaults are seven LODs and mesh size 48. Measure actual visible radius,
silhouette quality, and GPU cost at the target horizon distance before claiming
the clipmap replaces vanilla terrain LOD. See `native/terrain3d/src/terrain_3d.h`.

### Separate grass discovery from broad terrain import

Keeping grass in the unified system is accepted scope. It is not free: current
`TerrainGrassParticles.observe_cell()` rebinds every live emitter after every
observed cell. A whole-world background fill turns that into repeated
RenderingServer work. Profile it and either batch grass discovery, make it
near-camera-priority only, or demonstrate the cost is negligible.

### Remove unsupported claims

- `prewarm_terrain_textures` currently defaults to `true` in
  `project/world_streamer.gd`. The claim that testing has run with it disabled
  "for a while" needs evidence or removal.
- Pre-registering every blank region does not merely show a neutral flat plane:
  it creates zero-height, unpainted regions, which this fork intentionally
  renders with an obvious placeholder. Treat prewarming as a measured fallback,
  not an expected path.
- The vanilla LOD section needs URLs, inspected real FNV paths, and a clear
  distinction between direct observation and inference. It is not adequate to
  label unsupported text "confirmed by web research".

## Required acceptance tests

Before declaring the first implementation pass complete, add and run tests for:

1. Real LAND census/bounds/gaps for each terrain-owning worldspace.
2. Adjacent-cell seams across heights, normals, VCLR, all N=7 ID/weight maps.
3. A counter/assertion proving WorldStreamer performs no terrain import.
4. Queue priority, cancellation, and duplicate suppression.
5. Spawn-safe readiness including terrain collision.
6. Exterior → interior → same exterior visibility/collision restoration.
7. WastelandNV → Freeside → WastelandNV isolation and retained residency.
8. Measured object-streaming frame cost while the terrain queue fills.
9. Actual distant-silhouette coverage at the chosen clipmap settings.

## Recommended phase boundary

Phase 1 should be deliberately narrow: extract the existing current terrain
behaviour into TerrainStreamer with one owner and no change in data fidelity or
scheduler policy. Prove ownership, readiness, pause/resume, and parity.

Only then implement detached worker preparation and benchmark its main-thread
commit. Continuous whole-world fill belongs after those two pieces are proven,
not before. Otherwise the plan combines lifecycle migration, native ESM indexing,
threading, render uploads, worldspace persistence, and horizon tuning into one
debugging failure.
