Phase 4 lifecycle detail added to the plan since the initial 1.3 draft.

## Verdict

1.3 is sound. Every claim checked this pass verified correctly against source,
including content this reviewer did not author (the expanded Phase 4
inactive-cache/resume operation). No blocking corrections from the last two
review rounds remain unresolved. Two real, non-blocking gaps found — both
about internal consistency between sections, not new factual errors.

## Findings

### 1. Phase 4's per-worldspace registry presupposes the texture-pool design Phase 0 leaves open

Phase 0's blocking callout ("texture pool cannot be shared as-is") explicitly
leaves two designs open, to be chosen before Phase 1 starts:

1. an independent `Terrain3DTexturePool` + bridge per worldspace, or
2. a shared logical catalogue (normalized source images + a stable
   LTEX-to-logical-slot mapping) replayed into each worldspace's own
   independent asset pool.

Phase 4's per-worldspace registry is written as a literal struct:

```
{ terrain, bridge, grass, texture_pool, queue_state, generation, resident }
```

The `texture_pool` field name presupposes design (1) — a distinct pool object
per registry entry. Under design (2), a worldspace's entry wouldn't hold a
`texture_pool` object at all; it would hold whatever state represents "this
worldspace's asset pool, populated by replaying the shared catalogue in a
stable order" (e.g. a replay cursor/version, or just the resulting per-
worldspace `Terrain3DAssets` binding with no separate pool object).

**Fix**: make the registry entry's texture-related field conditional on
whichever design Phase 0 actually picks, rather than hard-coding option (1)'s
shape in Phase 4's own task list. This is a one-line rewrite once the Phase 0
decision lands, not a design problem — but as written today it quietly
answers a question the plan says is still open.

### 2. Phase 3's per-cell queue state machine doesn't account for Phase 2's per-region staging granularity

Phase 3 defines a per-cell state machine keyed by `(worldspace, coord)`:

```
unseen → queued → preparing → prepared → committed
```

Phase 2 establishes that multiple cells sharing a single 256×256 Terrain3D
region must be composed by **one serial owner** before publication — a
region-level step, not a cell-level one. A worker finishing one cell's staged
payload doesn't mean that cell's region is ready to publish if a neighboring
cell contributing to the same region hasn't finished yet.

As written, it's ambiguous whether `prepared` means "this cell's own staged
payload is ready" (cell-level) or "this cell's entire region, including every
contributing cell, is ready to publish" (region-level) — and whether
`committed` can happen independently per cell, or must happen atomically for
every cell in a region at once.

**Fix**: state explicitly that `committed` is a region-level transition —
every cell contributing to a given region moves from `prepared` to
`committed` together, at the moment the serial region composer publishes that
region via the Phase 2 batch API. A cell can sit in `prepared` for a variable
amount of time waiting on a slower neighbor before its region's composer runs;
that's expected, not a bug, but the plan should say so rather than leave the
granularity implicit.

## What's already good — verified, not just asserted

- The Phase 4 inactive-cache/resume ordering (visibility → physics-process →
  collision → grass processing/emitters, and the exact reverse on resume) is
  grounded in real API, checked directly: `TerrainGrassParticles`
  (`project/gamebryo/terrain_grass_particles.gd:1-2`) genuinely owns
  `GPUParticles3D` nodes with `.emitting` (line 229) and `.restart()`
  (line 177) — the plan's handling of both is accurate, not invented.
- `Terrain3DCollision.DISABLED`/`DYNAMIC_GAME` usage matches this project's
  own already-established pattern in `world_streamer.gd`'s existing
  `set_paused()`.
- Every prior round's blocking correction (worker-safety wording consistency,
  `set_camera()` no-op fix, data-service ownership, readiness return
  contract, per-transition call sequence, texture-memory split) remains
  correctly reflected in the current file — no regressions from earlier
  rounds reintroduced.

## Recommendation

Neither finding blocks Phase 0 research. Both should be folded in before
Phase 1 implementation starts, since Phase 1 is where `TerrainStreamer`'s
registry shape and Phase 3's queue state machine actually get built — fixing
them now is cheap; discovering the ambiguity mid-implementation is not.
