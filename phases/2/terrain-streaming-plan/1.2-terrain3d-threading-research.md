# Terrain3D threading research — 2026-08-26

This corrects the overly broad worker-boundary claim in `1.2-feedback.md`.
The objective is to take as much terrain import work off the main thread as the
actual Terrain3D implementation supports, not to preserve the current
per-pixel GDScript commit path by default.

## Evidence

### Godot's actual rule is not “all resources on the main thread”

Godot documents a useful distinction: modifying the same unique resource from
multiple threads is unsupported, but resources can be loaded and manipulated
on a worker before being added to the active scene. Active SceneTree
interaction is not thread-safe. Rendering/Physics server work from a worker
requires the relevant separate-thread project settings, and GPU/image work can
introduce synchronization stalls.

- [Godot: Thread-safe APIs](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)
- [Godot: RenderingServer](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html)

The project does not set Godot's rendering-driver separate-thread or
PhysicsServer3D separate-thread settings in `project.godot`; do not assume
worker-thread RenderingServer/PhysicsServer calls are enabled in the current
runtime configuration.

### Current vendored Terrain3D has no active-data synchronization

The local `native/terrain3d/src/` tree contains no mutex/thread ownership
around `Terrain3DData`, `Terrain3DRegion`, or generated map textures. The
important paths are:

- `Terrain3DData::set_pixel()` directly writes the `Image` held by an active
  `Terrain3DRegion` and marks it modified (`terrain_3d_data.cpp:749`).
- `add_region()` mutates the active `_regions` dictionary and
  `_region_locations` array (`terrain_3d_data.cpp:226`).
- `update_maps()` rebuilds those active collections, emits `maps_changed` and
  per-map signals, and either rebuilds or updates all generated texture arrays
  (`terrain_3d_data.cpp:467`).
- `GeneratedTexture::create()`/`update()` directly invoke
  `RenderingServer::texture_2d_layered_create()` and
  `RenderingServer::texture_2d_update()` (`generated_texture.cpp:25`).
- `Terrain3DCollision::update()` reads current terrain state while changing
  physics shapes (`terrain_3d_collision.cpp:286`).

Therefore, **the current live Terrain3D import API is not safe to call from
multiple workers concurrently**. This is not a generic Godot assertion; it is
the absence of synchronization in the exact shared data structures and server
calls this project would race.

That does **not** mean the imported region content must be prepared on the
main thread.

## Recommended high-throughput architecture

### Worker-owned staged regions

Workers should perform all expensive, pure/import-side work:

1. private `EsmReader` LAND lookup/decompression;
2. grid conversion and canonical shared-edge ownership masking;
3. expansion of LAND/VCLR/VNML/VTXT into the project's eight final map
   payloads: height, control, colour, TEX_ID_A/B, WEIGHT_A/B, normal;
4. construction and filling of **new, worker-owned** `Image` objects (or raw
   byte/float buffers converted to those Images); and
5. optionally, construction of a new, detached `Terrain3DRegion` containing
   only those Images.

No worker may retain a reference to a region/image after publishing its staged
result, and no staged image can also be referenced by a currently active
Terrain3D region. Multiple cells which contribute to the same 256x256 region
must be composed by one serial owner (a per-region staging job, or a locked
staging buffer) before publication. Do not solve that with workers writing
different portions of the live region.

### Short main-thread publication

The main thread should do only work that must touch active Terrain3D state:

1. resolve LTEX FormIDs through the active world's slot table;
2. create/replace the active region and attach the completed staged maps;
3. update the region index and generated map textures once per bounded batch;
4. schedule/perform the required collision update; and
5. update material bindings/grass only after publication.

The existing `import_cell()` API cannot do this efficiently: it calls
`set_pixel()` thousands of times from GDScript against live maps. Add a small
native Terrain3D extension API for batch publication (for example, accepting a
detached region or eight completed Images, with one region-index/map update at
the end). This is the worthwhile Terrain3D fork change. It removes the
per-pixel GDScript↔GDExtension overhead while retaining a clean ownership
handoff.

### What remains unsafe without a larger Terrain3D redesign

Keep these on the main thread in the first implementation, because they
mutate shared active state and/or use servers in the current default project
configuration:

- live `Terrain3DData.set_pixel()`, `add_region*()`, and `update_maps()`;
- `Terrain3DAssets.set_texture()` and material LUT writes;
- `GeneratedTexture` rendering-server texture creation/update; and
- `Terrain3DCollision` build/update and scene-node visibility/camera changes.

This is not a permanent theoretical limit. A later Terrain3D fork could use
double-buffered region/map-array RIDs and a render-thread command queue, with
an atomic main-thread swap, and similarly stage raw height-field physics data.
That is an invasive renderer/physics ownership change. It should be separately
benchmarked and stress-tested, not slipped into the streaming refactor.

## Required proof before adopting the wider boundary

Add a repeatable Terrain3D thread-boundary test, not a one-off “it did not
crash” run:

1. workers build many unique detached 256x256 eight-map region payloads while
   the game renders and collision queries continue;
2. publish batches on the main thread while moving the camera across their
   boundaries;
3. repeatedly pause, deactivate, and change worldspace, asserting no stale
   generation can publish;
4. verify every map byte and shared edge against the expected payload after
   randomized job completion; and
5. record frame-time p50/p95/max and main-thread time against the current
   per-pixel import baseline.

Only if the detached resource construction itself fails this test should the
worker boundary retreat to raw arrays. Only if a deliberately engineered
Terrain3D double-buffer/server path passes an equivalent test should live
upload/collision work move farther off-thread.

## Consequence for plan 1.2

Phase 2 should be reframed from “detached LAND arrays then main-thread
per-pixel writes” to **worker-built staged region maps plus native batched
main-thread publication**. This is both safer than concurrent mutation of
active Terrain3D resources and materially more aggressive about removing work
from the main thread. It deserves a focused prototype/benchmark before the
whole-world fill is implemented.
