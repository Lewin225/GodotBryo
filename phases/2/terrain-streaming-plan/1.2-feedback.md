# Terrain streaming plan 1.2 — review feedback

Reviewed against `1.2-plan.html` and current master on 2026-08-26.

## Verdict

1.2 is the first version that has a credible implementation shape. It answers
the substantive 1.1 review rather than papering over it:

- `Game`/`TerrainStreamer`/`WorldStreamer` ownership is now named.
- readiness is a generation-tagged query rather than a pair of losable
  signals;
- the queue has an authoritative coordinate source, states, reprioritisation,
  duplicate suppression, and fairness; and
- the live-resource worker boundary is correctly intended to be fixed on the
  main thread.

**Phase 0 may start. Phase 1 should not start until the corrections below are
folded in.** They are not redesigns; they are missing details that would
otherwise make the new lifecycle fail in the exact transitions this plan is
meant to protect.

## Preferred threading option — replace per-pixel main-thread import

After inspecting Terrain3D itself, the preferred Phase 2 design is **not**
“workers decode LAND, then the main thread calls `set_pixel()` thousands of
times.” It is:

1. workers decode LAND and construct complete, detached 256×256 staged region
   maps for all eight project map types;
2. one owner composes each staged region and applies the canonical shared-edge
   rule before it is published; and
3. a small native Terrain3D fork API attaches/replaces the completed region
   maps and updates generated textures once per bounded main-thread batch.

That moves both ESM work and map construction off the main thread, eliminates
the GDScript-to-GDExtension per-pixel loop, and avoids concurrent mutation of
Terrain3D's live region data. The current vendored Terrain3D implementation
has no synchronization around its active region collections; `update_maps()`
also emits signals and calls RenderingServer texture uploads, while collision
reads live terrain state. Do not write those active structures concurrently
from workers as the code stands.

This is a preferred, evidence-based first implementation—not an assertion
that Godot resources are universally main-thread-only. Godot permits
worker-side resource construction before handoff, but does not support
concurrent mutation of the same unique resource. Full evidence, the proposed
batch API boundary, and required stress test are recorded in
`1.2-terrain3d-threading-research.md`.

## Blocking corrections

### 1. The document still contradicts itself on worker safety

The Phase 2 section correctly proposes a detached-payload boundary, while
Phase 0 still says all Terrain3D/Resource mutation stays main-thread-only
“until a dedicated thread-safety test proves a narrower safe boundary,” and
Phase 2's exit condition still requires “the thread-safety test exists and
passes.” Those are incompatible statements and must be reconciled.

My earlier demand to make the former an absolute rule — “every Godot resource
and Terrain3D operation stays main-thread-only; no test can broaden that
boundary” — was not justified. Godot's own thread-safety guidance is more
precise: manipulating a resource on a worker and later attaching it to the
active scene can be supported, whereas concurrently modifying the same unique
resource is not; active SceneTree interaction remains unsafe. Terrain3D's
specific native classes and its `set_pixel()`/upload/collision paths have not
yet been tested under this project's Godot 4.7 configuration, so neither a
blanket main-thread ban nor a blanket worker-safe conclusion is evidence-based.

Replace both versions with a scoped research gate:

> Phase 0/2 will audit and stress-test each proposed worker operation under
> this build: detached LAND data, detached Image/resource construction,
> active Terrain3DData/region writes, texture asset changes, map upload, and
> collision updates. The chosen boundary is the narrowest combination proven
> correct under concurrent rendering/physics and measured to improve frame
> time. SceneTree changes remain deferred to the main thread.

The test needs repeatable concurrent import, rendering, collision queries,
pause/deactivate cancellation, and thread-safety checks enabled; it must run
long enough to catch corruption rather than merely “not crash once.” Keep the
currently safe detached-payload implementation as the baseline, but do not
preclude a proven wider Terrain3D-specific path. Rename the exit criterion to
a *thread-boundary audit and stress test*, not merely a detached-payload test.

### 2. The proposed pause/resume flow will leave Terrain3D frozen

The plan correctly expands pause ownership to processing and camera binding,
but it does not specify the required re-enable operation. This is observable
from the vendored source:

- `Terrain3D.set_camera(camera)` calls `set_physics_process(true)` only when
  the supplied camera differs from `_camera`.
- A paused Terrain3D whose physics processing was disabled retains that same
  camera pointer.
- Calling `set_camera(the_same_camera)` on resume is therefore a no-op and
  does **not** resume clipmap snapping or dynamic collision updates.

Define and test an explicit resume sequence, e.g. restore/validate the active
camera then explicitly re-enable Terrain3D physics processing, before enabling
collision/readiness. Do not rely on `visible = true` or a repeated
`set_camera()` call. The Phase 1 exterior → interior → same exterior test must
move the camera after return and prove clipmap rings and collision update again.

### 3. `TerrainStreamer`'s data-service dependencies are still missing

Today `WorldStreamer._ready()` owns the main-thread `EsmReader` and
`GamebryoMeshResolver`; its terrain bridge and grass system consume those
instances. Moving only the four terrain fields leaves an unanswered question:
where do TerrainStreamer's main-thread ESM reader, mesh/texture resolver, and
Phase 2 private reader contexts come from?

Choose and state one lifetime model:

- TerrainStreamer owns a long-lived main reader/resolver and a worker-context
  pool; or
- `Game` owns and injects a shared main-thread data service into both
  streamers, with workers retaining their own private readers.

The choice matters. The second option preserves one decode cache; the first
may duplicate decoded DDS resources. The current claim about shared decoded
images across resident worldspaces is only true if the same resolver cache is
actually retained and used. Add this to the Phase 1 topology and Phase 0 memory
measurement rather than letting each new class silently construct a resolver.

### 4. `await_ready_for()` needs a concrete completion result and ownership

GDScript awaits do not have implicit promise rejection semantics. “Resolve or
reject deterministically” is not an API. Define a return/status contract such
as `READY`, `CANCELLED`, and `SUPERSEDED`, including who owns the generation,
how waiters are released on `pause`, `deactivate`, and a new activation, and
what `game.gd` does for each status. In particular, a cancelled old exterior
transition must not unfreeze a player belonging to a newer transition.

Also replace “target coordinate's own neighbourhood” with a named, testable
set (for example, the spawn cell plus the cells required by the actual
Terrain3D collision coverage measurement). GPU completion is only a legitimate
condition if Phase 0 finds an observable completion boundary; do not make a
readiness promise against a renderer fence that the addon/Godot API does not
expose.

## Important amendments

### Specify the Phase 1 desired-set source, not only its priority hint

TerrainStreamer self-querying the viewport camera is a reasonable response to
the camera-injection suggestion and matches WorldStreamer's established
pattern. It still needs an explicit statement that it independently computes
the current-radius desired terrain coordinates on its own cadence. A call from
WorldStreamer for “the tile I am about to populate” is a priority hint only;
it cannot be the source of phase-one parity because object queue throttling,
missing cells, and terrain import timing are different concerns.

State whether TerrainStreamer tests LAND presence itself before queuing, and
whether its current-radius/budget semantics deliberately match the live
Terrain3D path rather than merely its nominal radius.

### Make the edge rule executable

“Lower x, then lower y owns a shared edge” is now a sensible default, but
write the actual half-open sample-domain rule. It must say which west/east and
north/south row/column a committing cell skips, and which cell owns a shared
corner. Otherwise two correct-looking implementations can choose opposite
boundaries. The optional Phase 0 equality measurement can remove unnecessary
masking only after it proves equality for every authored map, not merely
height.

### Tighten the topology wording

`Game` does not deactivate WorldStreamer on an ordinary exterior → interior
door: it pauses it to retain the exterior state. Describe the matching calls
per transition explicitly:

- exterior → interior: pause both streamers;
- interior → same exterior: resume both;
- exterior → another worldspace: transition both by generation, with the
  outgoing terrain hidden/retained only when Phase 4 provides the registry.

This makes the Phase 1 single-world lifecycle and Phase 4 multi-world
lifetime boundary unambiguous.

### Add `game.tscn` and the injection/wiring site to the Phase 1 file list

The plan correctly observes that Terrain3D is currently a child of
WorldStreamer. Making TerrainStreamer a sibling requires a scene node and
references in `game.gd`; it is not represented in the Phase 1 files list.
Include `project/game.tscn`, plus whichever script owns the data-service
injection chosen above.

## What is now good enough

The reply successfully fixes the previously fatal queue and ownership
ambiguities. The two-phase split before global fill is now justified, the
debug-tab private-field dependency is explicitly in scope, and the corrected
texture-memory wording distinguishes raw DDS decoding from Terrain3D-bound
normalised assets. Keep those decisions.

After the four blocking corrections are incorporated, start Phase 0 only.
Phase 1 should remain gated on the census, texture-pool design decision,
measured collision/readiness boundary, and the explicit APIs above. Do not
allow “the plan says TerrainStreamer owns it now” to substitute for those
contracts.
