# Phase 0: terrain worldspace census

Status: first factual census complete on the local legal game-data copy. This is the finite queue-domain input for plan 1.5, not yet a throughput or clipmap benchmark.

## Method

Built and ran `native/tools/terrain_worldspace_census.cpp` against every shipped master:

```bash
cd native/tools
./build_terrain_worldspace_census.sh
./terrain_worldspace_census \
  ../../fresh_nv_copy/Data/FalloutNV.esm \
  ../../fresh_nv_copy/Data/CaravanPack.esm \
  ../../fresh_nv_copy/Data/ClassicPack.esm \
  ../../fresh_nv_copy/Data/DeadMoney.esm \
  ../../fresh_nv_copy/Data/GunRunnersArsenal.esm \
  ../../fresh_nv_copy/Data/HonestHearts.esm \
  ../../fresh_nv_copy/Data/LonesomeRoad.esm \
  ../../fresh_nv_copy/Data/MercenaryPack.esm \
  ../../fresh_nv_copy/Data/OldWorldBlues.esm \
  ../../fresh_nv_copy/Data/TribalPack.esm
```

Add `--csv /tmp/terrain-worldspace-queue.csv` to export the exact usable coordinate set. The full-master run produced 42,020 per-file payload entries; that CSV deliberately retains the nine Lonesome Road Wasteland overrides so a future load-order resolver can replace, rather than accidentally lose, the base entries.

The tool intentionally walks real exterior `CELL`s and verifies each coordinate through `find_exterior_cell()`, which excludes a WRLD persistent cell even if it carries an `XCLC`. It then matches the live `EsmReader.get_land_data(cell_form_id)` behaviour exactly: only the first `LAND` child is considered, and it enters the queue only when it decodes to a usable `VHGT` payload. This is stricter, and more useful, than counting every record tagged `LAND`.

For the region calculation it uses the committed `Terrain3DBridge` transform: a 33×33 LAND patch spans 32 terrain samples per axis; Bethesda +Y maps to Godot −Z; and Terrain3D regions are 256 samples. The legal Terrain3D region range is −16…15 in each axis (`REGION_MAP_SIZE = 32`).

## Results

Each 256² region has eight maps: two `RF` (4 bytes/pixel) and six `RGBA8` (4 bytes/pixel). That is exactly 2 MiB raw map data per fixed region layer before colour mipmaps, GPU/driver allocation overhead, collision, or ground-texture assets.

|---|---:|---:|---:|---:|
| WastelandNV | 16,388 | 80 | 18×18 = 324 | 648 MiB |
| TheStripWorldNew | 4,095 | 13 | 9×9 = 81 | 162 MiB |
| WastelandNVmini | 4,096 | 17 | 9×9 = 81 | 162 MiB |
| Lucky38World | 4,096 | 10 | 9×9 = 81 | 162 MiB |
| NVDLC02ZionCanyon | 4,096 | 19 | 9×9 = 81 | 162 MiB |
| NVDLC03BigMT | 4,096 | 27 | 9×9 = 81 | 162 MiB |
| NVDLC04DivideVistaWorld | 4,096 | 5 | 9×9 = 81 | 162 MiB |

All remaining terrain-owning worldspaces are materially smaller: eight further base-game worldspaces, eight Dead Money worldspaces, one small Old World Blues worldspace, and seven separate Lonesome Road worldspaces. Every surveyed worldspace fits the current 32×32 Terrain3D coordinate limit at `REGION_SIZE = 256`.

The four item-pack masters (`CaravanPack`, `ClassicPack`, `GunRunnersArsenal`, and `MercenaryPack`) contain no terrain-owning worldspace.

The Wasteland queue is sparse rather than a filled 130×130 rectangle: its real usable cells span `x = −65…63`, `y = −65…64`, with 382 absent coordinates in that bounding rectangle. Its actual terrain touches 292 regions, but fixed stable allocation needs the complete 18×18 coordinate rectangle: 324 layers. This validates the plan's fixed-capacity approach and invalidates any termination strategy based on an unbounded spiral/no-cell cache.

## Important findings

1. **The DLC requirement is real.** Zion, Big MT, and Divide Vista are each a full 4,096-cell, 81-region terrain worldspace. They are not edge cases that can be deferred behind Mojave-only assumptions.
2. **The cache needs an authored-family boundary, not global retention.** Retaining every distinct terrain-owning worldspace would total about **1,876 MiB** of raw map arrays before mipmaps/overhead/assets. The agreed policy is now: retain the Mojave family and its bounded base-game subworlds across their internal transitions, but, after destination readiness, release that whole family when entering an isolated DLC family. Each DLC retains only its own related worldspaces while active.
3. **The current runtime cannot yet consume this DLC census.** `GameDataConfig` and `CellLoader` open only `FalloutNV.esm`. The census includes DLC to constrain the refactor and future multi-master loading; implementation must not claim DLC terrain support until the ESM load-order/override service exists.
4. **Lonesome Road overrides WastelandNV.** Its nine usable Wasteland LAND cells are overrides in the existing `WastelandNV` worldspace, not a second terrain node. The eventual multi-master LAND index must resolve load order and replace the base payload at the same `(WRLD, grid)` key. A naïve per-file union would double-count and render the wrong terrain.
5. **Placeholder LAND records are common in several small worldspaces.** The queue must use usable decoded first-LAND payloads, not record count. For example, base FreesideWorld has 45 usable payloads and 68 first-LAND placeholders without usable height data.

## Implementation consequence

The Phase 3 queue source must be a native, load-order-aware index with entries keyed by `(worldspace FormID, grid coordinate)` and a resolved winning LAND payload. It should expose both the exact queue coordinate set and the stable per-worldspace LTEX FormID set. Scanning a rectangle through `find_exterior_cell()` is acceptable for a diagnostic fallback, but is not the source of truth for a multi-master implementation.
