Terrain Streaming Plan

A working plan for issue #19: pull exterior terrain ownership out of cell streaming entirely and give it a dedicated Terrain3D-only pipeline that eventually covers the whole worldspace — so the Mojave's distant mountains render the way they do in the original game.

Target: github.com/Lewin225/GodotBryo #19 Touches: world_streamer.gd, terrain3d_bridge.gd, terrain3d_texture_pool.gd Status: pre-implementation — Phase 0 not started, topology/readiness/queue contracts now explicit
What changed from 1.0 — implementation review by Codex

1.0 had two false architectural assumptions, an unsafe threading conclusion, and missing contracts at the points where this system meets rendering, physics, and exterior transitions. This revision treats that review as correct — verified independently against source for the two most consequential claims before accepting the rest. Concretely:

  • Texture pool sharing was wrong, not just under-specified. Terrain3DTexturePool is bound to one Terrain3D instance's own .assets — it cannot serve a second worldspace's terrain as-is. Phase 4 now requires a real design decision instead of assuming one shared pool works.
  • The threading safety conclusion was wrong. No RenderingServer call inside set_pixel() does not mean a worker can safely mutate a live Image/Terrain3DRegion the main thread and renderer can observe concurrently. Phase 2 (new, split out from the old Phase 1) now scopes workers to detached data preparation only.
  • Phase boundary re-sequenced. Extraction (ownership/readiness/pause/parity), threading, and continuous whole-world fill were combined in 1.0. They're now three separate phases, each with its own exit signal, so a failure in one doesn't take the others down with it.
  • Missing contracts made explicit: LAND enumeration/termination, shared cell-border determinism under concurrent writes, spawn-safe player-release readiness, and pause/worldspace-switch/cancellation ownership (currently split across WorldStreamer.set_paused() with nowhere for it to move to).
  • Corrected: 8 generated Terrain3D map arrays in this fork, not 3; prewarm_terrain_textures still defaults true in committed code (only local testing has run with it off); a full Phase 0 benchmark task list replaces the vaguer "measure it" note.

What changed from 1.3 — consistency review by Claude

Two internal contracts were made explicit without silently selecting either remaining implementation policy: the Phase 4 registry no longer assumes one particular texture-pool design, and the Phase 3 cell queue now states how it relates to the Phase 2 region composer.

What changed from 1.4 — implementation decisions locked

The remaining alternatives are now decisions: stable LTEX identity slots are preassigned from metadata without preloading DDS assets; each worldspace owns the simple independent Terrain3D pool/bridge path; map-array capacity is preallocated for the census domain; and terrain publishes atomically by complete 256×256 region. Background fill continues while the player stands still until every real LAND region is resident.

What changed in 1.5 — final execution contract

The plan now names the concrete per-world registry field and ownership model, permits only detached worker-owned staging Images (never live Terrain3D state), and defines completion precisely: idle background fill reaches every censused LAND region; clipmap/frustum visibility remains a separately measured renderer-horizon requirement. No architectural alternative is left open for this first pass.

PHASE 0

Research & audit

The issue's own deliverable requires this to land as a comment before any code — real coverage figures, Terrain3D's real constraints, and a migration plan grounded in both, not assumption.

Worldspace coverage survey

  • Extend native/tools/terrain_census to report per-worldspace LAND record count, grid bounding box, and gaps within that box, for WastelandNV and every other terrain-owning worldspace (Freeside, at minimum). The census output is the queue domain for Phase 3's termination check — see below, not a separate document.
  • Cross-check against the region-count ceiling already discovered the hard way in terrain3d_bridge.gd: Terrain3DData's region map is a fixed 32×32 grid, which is why region_size was raised from 128 to 256. Confirm 256 still holds once the fill pushes real region residency to the worldspace edge.
  • Measure real per-region memory (all eight generated maps — see below — at region_size=256) so a "keep every worldspace resident, never evict" policy has an actual number behind it, not a guess.
  • Document Terrain3D's usable region-coordinate bounds against every surveyed worldspace's real grid extent, including the exact coordinate transform already worked out in cell_terrain3d_global_position() — this is what determines whether region_size=256 genuinely covers a given worldspace's edges, not just WastelandNV's.
  • Record a reproducible benchmark scene/script plus the hardware/settings it ran under, so throughput numbers from this survey stay comparable to whatever Phase 2 measures later.
Blocking — LAND enumeration decision

There is no current worldspace LAND index. EsmReader can locate an exterior CELL by grid through the ESM block/sub-block structure, then get_land_data() finds that CELL's LAND child — it cannot currently enumerate { grid, CELL, LAND } directly. Phase 0 must choose one finite source of truth for Phase 3's fill queue before that phase starts: either add a native worldspace LAND enumeration/index, or use the surveyed finite grid bounds above plus the existing indexed CELL lookup. An unbounded spiral plus a no-cell cache is not a termination policy on its own — the census above must produce the exact queue domain, present-LAND count, and missing coordinates per worldspace, and Phase 3 consumes that number directly.

Vanilla behavior

Direct fact vs. inference — kept separate on purpose

Directly documented: FNV's own Gamebryo terrain LOD is a real LOD4 / LOD8 / LOD16 / LOD32 hierarchy — pre-baked simplified meshes (Meshes\Landscape\LOD\<Worldspace>\*.NIF) plus baked diffuse/normal textures, grouped by cell-block size, generated offline. Source: Nexus Mods Wiki, LOD Generation For New Vegas and Fallout 3, Viva New Vegas LOD Guide. This matches the "reuse Bethesda's own pre-baked LOD data" approach already used for object LOD (phase 2.12, _lod.nif pairs); ROADMAP.md's Phase 2 bullet names it explicitly.

Not yet directly observed, and needs to be before Phase 3 sizes its fill radius: how far out the pre-baked LOD tiers are actually visible in real play before atmospheric fade/sky dome hides them, and separately, real Terrain3D clipmap coverage at this fork's actual settings (mesh_lods, mesh_size, vertex spacing — current native defaults are seven LODs and mesh size 48, see native/terrain3d/src/terrain_3d.h). Loading all LAND does not by itself prove distant mountains render — measure actual visible radius, silhouette quality, and GPU cost at the target horizon distance before claiming the clipmap replaces vanilla terrain LOD.

Open question

Issue #19 already commits to a different approach than the pre-baked-mesh one above — feeding Terrain3D's own clipmap LOD with continuously-streamed real LAND heightmap data. That's a deliberate fork from this project's stated default (reuse pre-baked data), not an oversight — worth a one-line confirmation that it's still the intended direction before Phase 3 builds on it, since the pre-baked LOD meshes are sitting right there as a lower-effort alternative.

Terrain3D capability check

  • Read native/terrain3d/src/terrain_3d_region.h / terrain_3d_collision.cpp directly to determine whether collision and grass can be scoped per region, or only globally the way set_collision_mode() is called on the whole Terrain3D node today, and confirm real collision coverage/update behavior immediately after a region commit — not assumed from the height/control write succeeding.
  • Measure the real clipmap horizon at the fork's actual mesh settings and compare it directly against directly-observed vanilla terrain visibility (not just the cited pre-baked-LOD configuration values above) — the two need to actually be compared side by side before claiming parity, not each measured in isolation.
  • Profile TerrainGrassParticles.observe_cell() under whole-world-fill conditions, not just nearby streaming: it currently rebinds every live emitter on every observed cell, and a background fill touching every cell in the worldspace turns that into repeated, cumulative RenderingServer work. Either batch grass discovery, make it near-camera-priority only, or demonstrate the cost is negligible — required before Phase 3 ships, not a nice-to-have.
Blocking — texture pool cannot be shared as-is

Corrected from 1.0, which assumed one Terrain3DTexturePool serves every worldspace's Terrain3D. Verified false: Terrain3DTexturePool._init(terrain) (terrain3d_texture_pool.gd:68) stores a single _terrain: Terrain3D, and every asset write goes through _terrain.assets.set_texture(...) — bound to that one instance's own Terrain3DAssets. A second Terrain3D (Freeside) would never receive those textures; its bridge would still emit texture IDs against a material LUT nothing populated.

Decision: use the simple, correct first pass — one Terrain3DTexturePool and one Terrain3DBridge per Terrain3D/worldspace. The Game-owned resolver retains its shared decoded-DDS cache, but each terrain owns its asset pool, material LUT, and bridge state. Do not build a shared logical asset catalogue in this implementation.

Corrected in 1.2: don't describe that per-worldspace texture cost as duplicated raw image data — it isn't. Terrain3DBridge already resolves ground textures through resolver.load_texture(...) (terrain3d_bridge.gd:565), i.e. GamebryoMeshResolver's existing path-keyed decode cache — the same DDS used by two worldspaces is decoded once and shared today, before any of this plan's changes. What is genuinely per-instance is the normalized, Terrain3D-asset-bound copy (Terrain3DTexturePool._normalize_texture()) and its slot-table/material binding (_terrain.assets.set_texture()). Phase 0's benchmark must report these two costs separately — shared decoded-image memory vs. per-Terrain3D asset/array bookkeeping — not one combined "texture memory" number.

Reconsidered, twice — tightened

prewarm_terrain_textures is still true by default in committed code (world_streamer.gd:155) — it exists only to work around a shader-regeneration corruption bug in the addon's own texture-add path, long since fixed. Local testing has run with it manually disabled, at the cost of a noticeably slower first paint on the exterior world as textures resolve lazily instead — but that is not the same claim as the code defaulting to off, and this doc should not conflate the two.

Decision: do not preload DDS textures merely to assign terrain IDs. Phase 0 enumerates the real LAND/LTEX metadata and freezes a stable, per-worldspace LTEX FormID → logical terrain slot table before worker staging starts. Workers receive that immutable table and can write final TEX_ID_A/B Images without a main-thread remap. Actual DDS decode/normalization/asset upload remains lazy; the bridge's per-world LUT maps each logical LTEX slot to its render-texture slot when that asset becomes available. This retains correct GRAS identity even when two LTEX records share a DDS, while avoiding the old full texture-preload cost.

Main-thread boundary audit — corrected

Read native/terrain3d/src/terrain_3d_data.cpp directly rather than assuming — the safety conclusion drawn from that read in 1.0 was wrong, even though the underlying fact was accurate:

Confirmed from source

Terrain3DData::set_pixel() (terrain_3d_data.cpp:749), which set_height() wraps, is just Image::set_pixelv() on the region's own CPU-side Image plus a set_modified(true) flag — no RenderingServer call, no signal, nothing GPU-facing inside that one call.

Blocking — corrected conclusion

That fact does not make the call worker-safe, and 1.0 was wrong to conclude it did. set_pixel() mutates an Image owned by an active Terrain3DRegion and changes region state that Terrain3D, the renderer, collision, and the main thread can all observe live. A per-region worker claim prevents two workers from writing the same region concurrently — it does not make concurrent mutation of a live Godot Resource safe against the main thread, which may be reading or rendering that same region at the same moment.

Workers may perform only detached preparation: ESM LAND lookup/decompression through a private EsmReader (the established GamebryoResolveContext pattern); coordinate conversion; decoded heights, normals, VCLR, VTXT opacity; and LTEX FormIDs — prepared arrays keyed by the real LTEX FormID, not a final render-slot ID (slot resolution touches the shared texture pool and must stay main-thread, see the texture-pool decision above).

Revised in 1.3 — the prior "main-thread-only, full stop, no test can broaden this" framing overcorrected. Godot's own rule is narrower than that: concurrently mutating the same active, live resource is unsafe, but constructing a new, detached resource on a worker and handing it off before it joins the active scene is a supported pattern. Verified directly: this project doesn't enable rendering/rendering_thread_model or a PhysicsServer3D separate-thread setting in project.godot, so calling RenderingServer/PhysicsServer3D from a worker isn't available under the current runtime configuration regardless — but that only rules out live server calls from workers, not worker-side construction of plain data or detached Godot objects. See Phase 2 for the actual worker/main split this implies.

  • Region creation (ensure_regions_for_cell() → add_region_blank(), mutates terrain.data.region_locations directly), first-time texture resolution (Terrain3DTexturePool.get_slot(), creates/normalizes a real Texture2D), and post-loop bookkeeping (update_maps()/calc_height_range()/set_edited(), regenerates GPU texture arrays and emits *_changed signals) all confirmed main-thread-only, unchanged from 1.0's finding.
  • Real hazard, not incidental: two adjacent cells can share a boundary region — import_cell()'s own header comment documents this for odd grid coordinates. A per-region worker claim prevents two workers racing on the same region's write, but does not prevent nondeterministic last-writer-wins values at a shared edge when worker completion order varies run to run. See Phase 2's shared-edge contract below — this needs either a canonical edge-ownership rule or a proven, deterministic commit order with a regression test, not just a lock.

Map/upload cost — corrected

Blocking — understated in 1.0

1.0 described three generated Terrain3D map arrays. This fork has eight: height, control, colour, TEX_ID_A, TEX_ID_B, WEIGHT_A, WEIGHT_B, and normal — matching this project's own N=7 blend patch. Terrain3DData::update_maps(TYPE_MAX, false, false) updates every edited map layer; a full rebuild recreates all eight arrays. See native/terrain3d/src/terrain_3d_data.cpp.

The Phase 0 benchmark must separately measure, with real numbers, not a slogan: LAND read/decode/preparation cost; main-thread region creation cost; main-thread texture/asset resolution cost; per-cell map write cost (all eight arrays); incremental upload cost; full-array-rebuild cost when a new region is introduced; collision update cost, if enabled; and worst/p95/average frame cost across a real churn run. The current bridge performs thousands of GDScript-to-GDExtension pixel calls per cell — Phase 2's detached preparation may not move the real bottleneck at all if most of the cost is actually in those main-thread calls, not the data preparation. This must be measured before Phase 2 is scoped as "the" fix.

Exit signal — a GitHub comment on #19 with: real coverage/gap numbers per worldspace and the LAND enumeration decision; the texture-pool architecture decision (§ above); the pre-baked-vs-live-LAND confirmation; measured Terrain3D horizon coverage at real clipmap settings; the grass-discovery profiling result; and the full eight-map benchmark breakdown — before any of Phase 1 starts. This plan supersedes issue #19's older height-only wording; link the two so future work isn't misled by it.
PHASE 1

Extract ownership — parity only

Deliberately narrow, per review feedback: move current terrain behavior to a single new owner with zero change to import fidelity, scheduler policy, or which cells get terrain, relative to what game.tscn actually runs today — that scene already sets use_terrain3d = true (game.tscn:57), so removing the now-dead legacy toggle and its false class default is deleting unused configuration surface, not changing real runtime behavior; it was also already authorized in the 1.0 review round. No threading, no whole-world fill yet — those are Phases 2 and 3. Prove ownership, readiness, and pause/resume first, since everything after this depends on getting those three right.

New class: TerrainStreamer

  • Owns the shared Terrain3D node, Terrain3DTexturePool, Terrain3DBridge, and TerrainGrassParticles — all four currently live as WorldStreamer member fields, created in activate() and freed in deactivate(). Those four fields move out wholesale.
  • Imports terrain for exactly the same radius/cells WorldStreamer currently drives it for — this phase changes who imports, not what gets imported or how many cells. The continuous whole-world fill is Phase 3, deliberately sequenced after this and Phase 2 are both proven.
  • Gets its own diagnostics, mirroring the existing diagnostic_terrain_ms array and the opt-in freeze_trace_enabled pattern from issue #6 — a second independently-observable trace, not folded into WorldStreamer's.
Blocking — explicit hand-off topology, not implied by "TerrainStreamer owns X"

Verified this is a real scene-wiring change, not just a class extraction: Terrain3DBridge.create_terrain(self) is called as world_streamer.gd:263 — self is WorldStreamer, and create_terrain() literally does parent.add_child(terrain) (terrain3d_bridge.gd:120). Terrain3D is a real child of WorldStreamer in the live scene tree today. The interface must be named before coding, not left implicit:

  • Game (already the parent of both CellLoader and WorldStreamer, per game.tscn) owns TerrainStreamer as a third sibling, and calls the matching lifecycle method on it alongside the existing two, per transition type — see the explicit call sequence below.
  • TerrainStreamer derives its own grid coordinate the same way WorldStreamer already does — self-querying get_viewport().get_camera_3d() (_active_camera(), world_streamer.gd:402-404), not camera-injection from Game. Kept on this project's own established pattern rather than a new supply mechanism.
  • Added, per review: this is more than a camera-source statement — TerrainStreamer independently computes its own desired terrain-coordinate set on its own cadence, the same way WorldStreamer._check_streaming() computes its own resident set today. A WorldStreamer priority call is a hint that re-prioritizes an already-desired coordinate, never the sole source of what gets imported — object-queue throttling, missing-cell handling, and terrain import timing are different concerns with different budgets, and conflating them was exactly what made "parity" ambiguous in 1.2. TerrainStreamer tests LAND presence itself (via whichever enumeration Phase 0 chose) before queuing a coordinate, independent of whether WorldStreamer has any REFR content there at all.
  • WorldStreamer may call exactly one narrow method on TerrainStreamer: request_terrain_priority(coord: Vector2i). It must not hold a Terrain3D/bridge/pool reference of its own, and must not read or decide terrain state.

Added, per review — data-service ownership. WorldStreamer._ready() currently owns the main-thread EsmReader/GamebryoMeshResolver (world_streamer.gd:235,238) and hands them to the terrain bridge on construction. Once TerrainStreamer is its own class, that source disappears. Decision, chosen now: Game owns and injects one shared main-thread EsmReader/ GamebryoMeshResolver pair into both streamers, rather than each streamer constructing its own. Workers still get their own private per-task readers (the established GamebryoResolveContext pattern, unaffected). This is the option that actually preserves the one-decode-cache property the corrected texture-memory claim above depends on — a `TerrainStreamer`-owned duplicate resolver would silently reintroduce duplicate DDS decodes across worldspaces, undermining that claim. Phase 0's memory measurement must confirm the shared cache is genuinely retained and hit under this model, not assumed.

Added, per review — explicit per-transition call sequence, since Game pauses WorldStreamer on an ordinary exterior→interior door rather than deactivating it (existing behavior, unchanged):

  • Exterior → interior: pause both WorldStreamer and TerrainStreamer.
  • Interior → same exterior: resume both.
  • Exterior → a different worldspace: transition both by generation (Phase 1's single-active-world lifecycle: today's deactivate()-then-activate() shape). The outgoing terrain is hidden-and-retained across a worldspace switch only once Phase 4 provides the multi-world registry — Phase 1 alone still tears down and rebuilds on a worldspace change, exactly like today's behavior it's replacing.

WorldStreamer changes

  • Delete the entire use_terrain3d branch inside _stream_tile() — both sides. The legacy, non-Terrain3D GamebryoTerrainBuilder mesh path is deprecated and removed outright, not preserved as a parallel system. TerrainStreamer becomes the only terrain path; use_terrain3d, terrain_root, and CellStreamBuilder.build_terrain()'s call site all go away with it.
  • Cell streaming may request priority for the coord it's about to populate — a plain method call into TerrainStreamer, not an import — but never touches Terrain3D itself.
  • Added, verified: world_streaming_debug_tab.gd:145 currently reads _world_streamer._terrain3d_pool directly — a private-field dependency this extraction breaks outright, not a cosmetic one. Move texture-pool and terrain-queue status display to TerrainStreamer (or a new dedicated terrain debug tab) as part of this phase, not left stale.
Blocking — spawn-safe readiness contract

"The requested coordinate landed" is not a sufficient readiness signal, and 1.0 only gestured at this. The transition contract this phase must actually define:

  • Exactly which cell/neighbourhood must have committed height data before release — not just enqueued or in-flight.
  • Whether Terrain3D collision must be built and enabled before release, not just height data present — a player released onto committed-but-collisionless terrain falls through it.
  • Whether GPU upload completion is required before release, or whether committed CPU-side data is sufficient (ties directly into the incremental-vs-full-rebuild upload cost from Phase 0).
  • Cancellation behavior if the player changes worldspace mid-load — what happens to an in-flight readiness wait for a worldspace that's no longer the active one.

Corrected in 1.2: "await both readiness signals" is not enough on its own — confirmed by this project's own history, not just abstract caution. world_streamer.gd's own doc comment on set_paused(false) already documents a real bug of exactly this shape: _maybe_emit_settled() firing synchronously "with zero listeners connected yet — the emission is simply lost... leaving the player frozen forever," fixed only by routing through call_deferred(). A bare one-shot signal here would reintroduce that same class of bug at the terrain boundary.

Define a generation-tagged, queryable readiness predicate instead: await_ready_for(worldspace, coord, generation), whose first action checks already-committed state (so a caller attaching late still gets a correct answer, not a missed signal) and whose eventual completion re-checks it.

Corrected in 1.3: "resolve/reject deterministically" isn't itself an API — GDScript's await has no implicit promise-rejection semantics. Concrete return contract: await_ready_for() returns one of READY, CANCELLED (pause/deactivate fired mid-wait), or SUPERSEDED (a newer activation/generation replaced this one before it resolved) — game.gd only releases the player on READY; a CANCELLED/SUPERSEDED result from an old transition must never unfreeze a player who now belongs to a newer one. TerrainStreamer owns the generation counter (bumped on every activate/deactivate, mirroring WorldStreamer._generation's existing role) and is responsible for releasing every outstanding waiter with the correct status on pause, deactivate, or a new activation.

"Target coordinate's own neighbourhood" is replaced with a named, testable set: the spawn cell plus whichever cells Phase 0's own real collision-coverage measurement shows are required for solid footing at that spawn point — not a vague radius. GPU-upload completion is only included in "ready" if Phase 0 finds an actual observable completion boundary in the Terrain3D/RenderingServer API; this plan does not promise readiness against a renderer fence that the addon or Godot doesn't expose. game.gd currently awaits only WorldStreamer.streaming_settled; this predicate replaces a hand-rolled two-signal race, it doesn't sit alongside one.

Blocking — pause ownership moves, doesn't duplicate — expanded scope

WorldStreamer.set_paused() currently owns Terrain3D visibility (visible = false) and collision (set_collision_mode(DISABLED)) for the interior-transition case. Those calls move into TerrainStreamer's own pause/resume lifecycle in this phase — not duplicated across both classes. This is already Phase 1's job, not Phase 4's (Phase 4 only extends a proven single-world lifecycle to a multi-world registry — it does not introduce lifecycle handling for the first time).

The lifecycle this phase owns is broader than visibility+collision alone, expanded per review: also processing (a hidden Terrain3D must not keep ticking clipmap/ collision work just because it's invisible — verify, don't assume `visible=false` already stops it), and camera binding — a real, already-found bug in this exact file: "Terrain3D's own clipmap LOD update... needs a real camera reference to position its rings... never set anywhere in this file before, so it silently failed" (world_streamer.gd, _check_streaming()'s own comment on _terrain3d.set_camera()). Once camera tracking moves to TerrainStreamer, it inherits responsibility for keeping that call live across pause/resume too. And readiness invalidation — any in-flight await_ready_for() call above must be cancelled/rejected on pause, not left dangling.

Corrected in 1.3 — verified against Terrain3D's own source, not assumed. Terrain3D::set_camera(p_camera) (terrain_3d.cpp:480-493) only calls set_physics_process(true) inside the branch where p_camera differs from the currently-stored _camera — confirmed by reading the source directly. Simply calling set_camera(_active_camera()) again on resume, the way _check_streaming() already does every tick, is a no-op for the common case (the player's camera identity doesn't change across a pause) and would not re-enable clipmap snapping or dynamic collision updates that pause disabled. Resume must call set_physics_process(true) on the Terrain3D node directly (a plain Node method, unrelated to set_camera()) as its own explicit step, not rely on the camera-set call to do it. The Phase 1 exterior→interior→same-exterior acceptance test must move the camera after return and prove clipmap rings and collision actually update again post-resume, not just that the scene looks visually unchanged.

PHASE 2

Detached worker preparation

New phase, split out of 1.0's combined Phase 1 per review feedback. Revised in 1.3 from a smaller design (worker prepares raw arrays, main thread calls set_pixel() thousands of times per cell) to a materially more aggressive one: workers construct entire staged region maps, and a new small native batch-publish API replaces the per-pixel commit loop entirely.

Blocking — the boundary is empirical and cited, not a permanent ban or a blanket clearance

Verified directly against the vendored source, not assumed either way: the current live Terrain3D import path has no synchronization around active state. Terrain3DData::set_pixel() writes the Image owned by an active Terrain3DRegion (terrain_3d_data.cpp:749); add_region() mutates the live _regions/_region_locations collections (terrain_3d_data.cpp:226); update_maps() rebuilds those collections and emits signals (terrain_3d_data.cpp:467); GeneratedTexture::create()/update() call RenderingServer::texture_2d_layered_create()/texture_2d_update() directly (generated_texture.cpp:25); Terrain3DCollision::update() reads live terrain state while changing physics shapes (terrain_3d_collision.cpp:286). None of these five paths is safe to call concurrently from multiple workers today — not a generic Godot caveat, the literal absence of synchronization in the exact structures this project would race.

That does not mean every step of an import must happen on the main thread — only the ones touching that live state. Godot's own documented rule is narrower than a blanket ban: a worker may construct a new, detached resource and hand it off before it joins the active scene; concurrently mutating the same active resource is what's unsupported. Treat the boundary below as the current evidence-based default, not a permanent theoretical limit — a later, deliberately engineered Terrain3D fork (double-buffered region/map-array RIDs, a render-thread command queue, atomic main-thread swap) could move the publish step itself further off-thread, but that's an invasive renderer/physics ownership change requiring its own benchmark and stress test, not something to slip into this phase.

Worker-staged regions, native batch publication

  • Worker task — all expensive import-side work: private EsmReader LAND lookup/decompression; grid conversion; expansion of LAND/VCLR/VNML/VTXT into the eight final map payloads; lookup through the immutable per-world LTEX logical-slot table; and construction/filling of new, worker-owned canonical Image objects. Workers never reference an active Terrain3D region, asset, texture, or scene node.
  • Complete-region publication — chosen: a 256×256 region is the only publication unit. Its composer schedules every LAND cell contributing to that region, owns their serial composition, and publishes exactly one completed immutable eight-map region. prepared means an individual cell payload is available; every contributing prepared cell advances to committed together when the region publishes. A cell may wait in prepared for a slower neighbour; this is expected. Near-spawn and near-camera priority operates on region groups, dispatching all contributors rather than waiting on an arbitrary cell queue. Do not implement incremental region snapshots in this pass.
  • Main-thread publication — deliberately short: attach the completed staged maps through the native batch-publish API; update the preallocated region-index entry and only that region's layers in the eight generated arrays; schedule/perform the camera-local collision update; then update material bindings and near-camera grass. No LTEX remap, per-pixel GDScript loop, format conversion, or mip generation belongs here.
  • New native scope, not present in 1.2: add a small batch-publication API to the vendored native/terrain3d/ fork — accepting a detached region or the eight completed Images, doing one region-index/generated-map update at the end, instead of import_cell()'s current thousands of GDScript-to-GDExtension set_pixel() calls. This directly removes the per-pixel call overhead Phase 0's benchmark is measuring, rather than just moving preparation off-thread and leaving that overhead in place.
Blocking — shared cell-border determinism, solved at staging time

Adjacent LAND cells write duplicate edge vertices. Since staged-region composition already happens once, serially, per region before publication (above), the canonical-owner rule becomes the masking policy applied during that staged construction, not a race resolved after the fact at commit time — a cleaner fit than 1.2's "publish then hope order doesn't matter" framing. Default policy, unchanged: the cell with the lower grid coordinate (lower x, then lower y) owns a shared edge's samples. Still needs the actual half-open sample-domain rule written out — which west/east and north/south row/column a non-owning cell skips, and which cell owns a shared corner — covering height, normals, colour, both texture-ID maps, and both weight maps. The regression test must still compare completed terrain under deliberately varied job completion order (which worker finishes which cell first, before the serial composer runs), since that's the real remaining nondeterminism once masking itself is fixed at staging time.

Publication policy — decided

A 256×256 Terrain3D region spans many 33×33 LAND-cell patches, and one cell can feed more than one region at a boundary. This implementation chooses complete-region atomic publication: compose every contributing cell once, then upload the region once. This avoids repeated multi-megabyte snapshots/uploads, preserves deterministic edges, and prevents flat/default partial terrain. If the Phase 2 benchmark shows unacceptable near-spawn latency, report it; do not silently add incremental snapshots.

Exit signal — a repeatable thread-boundary stress test, not a one-off "it didn't crash" run: (1) workers build many unique detached staged regions while the game continues rendering and querying collision; (2) batches publish on the main thread while the camera moves across region boundaries; (3) repeated pause/deactivate/worldspace-change asserts no stale-generation batch ever publishes; (4) every map byte and shared edge verified against the expected payload after randomized job completion order; (5) frame-time p50/p95/max and main-thread time recorded against the current per-pixel import_cell() baseline from Phase 0. If the benchmark shows the native batch-publish call itself still dominates regardless of staging, that's a valid, real finding this phase must report honestly rather than build past.
PHASE 3

Continuous outward terrain fill

Sequenced after Phase 1 (ownership/readiness/pause proven) and Phase 2 (threading proven and benchmarked) per review feedback — combining lifecycle migration, native ESM indexing, threading, render uploads, and whole-world fill into one pass was flagged as "one debugging failure," and that's the reason for the split. No second radius tier, no reduced-fidelity import path: TerrainStreamer fills outward from the player continuously until there is no worldspace left to import, at two speeds rather than two data profiles.

Blocking — corrected: queue mechanics, not a slogan

1.1 said the queue "only drains forward," which is false once the priority center can move — a min-heap ordered around a stale player coordinate is wrong the moment the player travels, and naively inserting priority requests creates duplicates and starvation. The direction (one queue, outward from the player, two speeds split at the existing LOD2 radius) stays correct; what was missing is the mechanics making that direction actually work:

  • Authoritative coordinate source is TerrainStreamer's own camera query (Phase 1's topology contract), never WorldStreamer._current_grid_coord() directly — that method stays private to WorldStreamer.
  • A per-cell state machine keyed by (worldspace, coord): unseen → queued → preparing → prepared → committed, with cancelled reachable from any non-terminal state (worldspace switch, pause, generation change).
  • Priorities are recomputed when the tracked center moves materially (a real distance threshold, not every tick) — not left stale from whenever a cell was first enqueued.
  • Duplicate suppression: a coord already in queued/preparing/prepared is never re-enqueued; a WorldStreamer priority request on such a coord re-prioritizes its existing queue entry instead of inserting a second one.
  • A fairness rule guarantees the low-priority whole-world fill still progresses even while the player continuously generates new near-priority work — e.g. a minimum guaranteed low-priority slot per tick, not "whatever's left over."
  • Fixed-capacity map arrays — chosen: after the Phase 0 LAND census, allocate the eight generated map arrays for the entire finite region domain of that worldspace and assign each region coordinate a permanent texture-array layer. Initialise uncommitted layers with canonical defaults; publish real LAND by updating its fixed layer in place. WastelandNV's likely 18×18 domain is roughly 648 MiB of raw map-array VRAM before mipmaps/overhead, an intentional modern-hardware trade for eliminating repeated full-array reallocations/uploads. This is census-driven per worldspace, not hard-coded to 324 layers.
  • Two throttle rates instead of two tiers: cells within WorldStreamer.RADIUS_LOAD_DISTANT (today's "LOD2", 20 grid cells) import at the existing responsive pace; cells beyond it import at a deliberately slower cadence — same import path, different budget, not a second code path.
  • Investigate resolving LAND directly by grid coordinate/FormID rather than find_exterior_cell() → full CELL resolution, using whichever LAND enumeration Phase 0 chose — the fill will eventually touch every coordinate in the worldspace, including many that never need REFR/CELL data at all.
  • Termination uses Phase 0's census output directly as the queue domain — present-LAND count and confirmed-missing coordinates per worldspace — not an unbounded spiral with an incidental no-cell cache. While the player is stationary, the fair background queue continues until every real LAND region is committed; diagnostics report committed regions: N / N and an empty queue. Once complete, moving anywhere in that worldspace performs no further terrain decode/staging/upload.
  • Grass discovery runs the batched/priority-gated approach Phase 0's profiling settled on, not observe_cell()'s current per-cell rebind unconditionally.

PHASE 4

Per-worldspace terrain lifetime

Terrain residency belongs to a worldspace family, not a reusable buffer. Switching from WastelandNV into Freeside must hide, not overwrite, WastelandNV's terrain; entering an isolated DLC family may deliberately release the Mojave family once the destination is ready. This phase is where the chosen per-worldspace texture-pool architecture gets built.

Fixed ownership — independent pool and bridge per worldspace

One Terrain3DTexturePool and one Terrain3DBridge belong to each Terrain3D/worldspace. The Game-owned mesh resolver remains the shared source DDS decode cache; each terrain retains its own normalized Terrain3D asset bindings, material LUT, and bridge state. Do not introduce a shared logical asset catalogue in this implementation. Per-worldspace accounting includes its real Terrain3D asset cost, not only heightmap data.

  • Replace WorldStreamer.deactivate()'s current behavior — _terrain3d.free(), unconditionally, on every worldspace switch — with a per-worldspace registry inside TerrainStreamer: { wrld_form_id: { terrain, bridge, grass, texture_pool, queue_state, generation, resident, cache_family } }. Each entry owns its independent Terrain3DTexturePool and bridge, bound only to that entry's Terrain3D assets/material. Phase 0's worldspace catalogue explicitly assigns cache families: the Mojave family includes WastelandNV and its bounded base-game subworlds; each isolated DLC family groups only its own related worldspaces. Do not infer this relationship from a numeric FormID prefix or an ESM filename at runtime.
  • Required inactive-cache operation — exact order: first mark the entry inactive and increment its generation, so no queued/prepared worker result may publish; suspend its queue while retaining only committed terrain state; then set terrain.visible = false, call terrain.set_physics_process(false), and call terrain.set_collision_mode(Terrain3DCollision.DISABLED). On the matching TerrainGrassParticles instance, set visible = false and set_process(false), and set every owned GPUParticles3D.emitting = false. Hiding alone is not a pause: it does not establish that Terrain3D clipmap/collision work or particle simulation has stopped.
  • Required activation/resume operation — exact order: select/create the entry; make its terrain visible; set its current active camera; call terrain.set_physics_process(true) explicitly (required even when the camera identity did not change); enable Terrain3DCollision.DYNAMIC_GAME; make grass visible, call grass.set_process(true), restore only locally-covered emitters to emitting = true, and restart them after their first active-camera coverage update; finally resume the queue under its new generation. Collision and grass must not be enabled before the terrain entry and active camera are restored.
  • Returning to a previously-loaded worldspace in the same cache family reactivates its retained instance rather than rebuilding it — no LAND re-import or texture-pool reassignment. The Game-level ESM/resolver cache is shared, but every entry retains its own Terrain3D map arrays, material bindings, bridge, collision state, grass node, and Terrain3D asset pool.
  • Explicit DLC-family eviction boundary: on a transition to a different isolated cache family, prepare the destination's spawn/near-camera terrain first. Once that readiness predicate succeeds and before handing control to the player, cancel and free every terrain entry in the outgoing family, including its subworlds; then activate the destination. This bounds resident map-array memory to the active family plus the one transitioning-in terrain, while preserving instant base-game transitions such as WastelandNV → Freeside → WastelandNV. Do not add general LRU or memory-pressure eviction in this pass.
Blocking — full pause/switch/cancellation lifecycle, not just the cross-worldspace case

The same inactive-cache operation applies to an ordinary exterior → interior transition, not only WastelandNV → Freeside. Pausing invalidates every in-flight worker publication by generation, retains committed maps and the uncommitted queue domain, and prevents all Terrain3D/collision/grass processing until resume. A result completing while paused is discarded and its coordinate becomes eligible for the resumed queue; it must never commit into a hidden entry. Returning to an exterior runs the ordered resume operation above and rebuilds only uncommitted work, never the retained terrain maps.

Exit signal — Goodsprings → Freeside → Goodsprings round trip: WastelandNV terrain reappears instantly on return, no re-import, no cross-contaminated region or texture data from Freeside, and the inactive Wasteland entry recorded zero Terrain3D physics ticks, collision updates, grass-process ticks, and emitting grass particles while Freeside was active. A separate exterior → interior → same exterior round trip: fill queue suspends and resumes correctly, no stale Phase 2 payload lands after a mid-transition worldspace switch, and camera motion after return proves clipmap and collision updates resumed. A Mojave → DLC-family transition proves destination readiness occurs before the Mojave family is freed, then proves every outgoing-family Terrain3D/bridge/grass/resource entry is gone and cannot accept a stale result. Returning to Mojave correctly rebuilds its terrain from the resolved LAND index.
TESTS

Required acceptance tests

Before declaring the first implementation pass complete, per review feedback — not optional polish:

  1. Real LAND census/bounds/gaps for each terrain-owning worldspace, including region-coordinate bounds vs. the real grid extent.
  2. Adjacent-cell seams across heights, normals, VCLR, and all eight N=7 ID/weight maps, under deliberately varied worker completion order — not just synchronous ordered imports.
  3. A counter/assertion proving WorldStreamer holds no Terrain3D/bridge/pool field and makes no bridge/grass call — only the documented request_terrain_priority() call.
  4. Queue state/ordering deterministic under duplicate requests and a moving player, demonstrating both near responsiveness and eventual low-priority background progress.
  5. Spawn-safe readiness via await_ready_for() including terrain collision, not just height data — including a transition cancelled/replaced mid-wait.
  6. Workers may construct exclusively-owned detached Image staging payloads, but are proven unable to read or mutate any active/shared Terrain3D resource, asset, texture, region, or scene node; a stale result cannot commit after pause/deactivate/world switch.
  7. Exterior → interior → same exterior executes the exact inactive/resume operation: hidden Terrain3D has physics processing disabled and collision disabled; grass root processing is disabled and every emitter is non-emitting; return explicitly restores camera, Terrain3D physics processing, collision, locally-covered emitters, and queue work.
  8. WastelandNV → Freeside → WastelandNV isolation and retained residency, with texture allocation/sharing measured directly across the two resident worldspaces, not inferred from the pool's object graph; diagnostics prove the inactive entry accumulated zero Terrain3D physics ticks, collision updates, grass-process ticks, and emitting grass particles.
  9. Mojave-family → DLC-family transition: destination spawn terrain becomes ready before the outgoing Mojave family is freed; all Mojave family terrain entries, queues, collision, grass nodes, and Terrain3D-bound assets are then released; no stale worker result can recreate one. A return to Mojave rebuilds only after that explicit eviction, rather than relying on an accidental retained entry.
  10. Measured object-streaming frame cost while the terrain queue fills.
  11. Actual distant-silhouette coverage at the chosen clipmap settings, measured against directly-observed vanilla visibility.
  12. The live debug UI (world streaming tab's terrain-pool display) remains functional after the ownership extraction.
v1.5: locks the remaining implementation choices. LTEX FormIDs receive stable logical slots from metadata before worker staging, without preloading DDS assets; actual texture decode and Terrain3D asset binding remain lazy. Each worldspace owns its own Terrain3D, bridge, and texture pool, while the Game resolver shares decoded DDS source data. Map-array capacity and coordinate layers are allocated once from the real LAND census; this deliberately spends modern VRAM to remove repeated array rebuild/upload churn. Publication is one completed, immutable 256×256 region at a time — no incremental snapshots. The background fill does not stop merely because the player does: it completes every real LAND region, after which movement does no terrain decoding/staging/uploading. Full residency is explicitly separated from finite clipmap/frustum visibility, which Phase 0 must compare directly with vanilla. Workers may build detached owned Images, but never access live Terrain3D state. These are validation gates, not remaining design forks: after Phase 0's factual census, capability checks, and benchmarks, the plan is ready for implementation. A subsequent Phase 0 census establishes that retaining every worldspace would cost about 1,876 MiB of raw maps before overhead, so the cache policy is now deliberately bounded by authored worldspace families: retain Mojave subworlds across their internal transitions, but release the entire outgoing family once an isolated DLC destination is ready.
