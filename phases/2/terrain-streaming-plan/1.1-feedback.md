# Terrain streaming plan 1.1 — review feedback

Reviewed against `1.1-plan.html` and current master on 2026-08-26.

## Verdict

This is materially better than 1.0. It retracts the two conclusions that made
1.0 unsafe: `Terrain3DTexturePool` is correctly recognised as bound to one
`Terrain3D.assets` instance, and workers are correctly restricted to detached
LAND preparation while every live Terrain3D/Godot resource mutation remains on
the main thread. The plan is now worth implementing, but it is **not yet an
implementation-ready contract**. The remaining holes are in ownership,
transition sequencing, and the precise queue semantics; those are exactly the
areas most likely to produce a visually plausible but race-prone replacement.

## Blocking corrections

### 1. Phase 1 has no complete hand-off contract

The plan says `TerrainStreamer` owns the Terrain3D node, bridge, pool, grass,
and terrain lifecycle, while `WorldStreamer` may only request priority. It
also says Phase 1 imports the same cells/radius WorldStreamer imports today.
Those statements do not define who supplies the camera, active worldspace,
desired terrain coordinates, initial spawn coordinate, or transition
lifecycle. A priority request is not a desired-set API.

Specify the public interface and its caller before coding. For example:

- `Game` owns both streamers (preferably as siblings), activates/deactivates
  and pauses both as part of a transition, and supplies the active camera.
- `TerrainStreamer` derives its own grid coordinate from that camera and owns
  its terrain desired set/queue.
- `WorldStreamer` may call only something narrowly named such as
  `request_terrain_priority(coord)`; it must neither access the Terrain3D
  object nor decide terrain state.

If a different topology is intended, write it down just as concretely.
Current code creates Terrain3D as a child of `WorldStreamer` and keeps the
four terrain fields there, so this is a real scene/wiring change, not merely a
class extraction. Include `game.tscn`, `game.gd`, and the affected debug UI in
the Phase 1 file list and acceptance tests.

### 2. Readiness must be a queryable state, not two bare signals

“Await both readiness signals” is insufficient. `game.gd` already has to deal
with a settled state being reached before a listener attaches; a one-shot
signal can be missed and leave a transition waiting forever. A stale signal
from the outgoing worldspace is equally dangerous.

Define a generation-tagged readiness predicate and await helper, e.g.
`await_ready_for(worldspace, coord, generation)`, whose first action checks
the committed state and whose completion re-checks it. Define the exact
neighbourhood, collision state, and upload state it means by “ready,” and
make cancellation resolve/reject deterministically when a transition supersedes
the request. Do not make `game.gd` hand-roll a two-signal race.

### 3. The Phase 1 “parity only” claim contradicts removing the switch

`use_terrain3d` is currently explicitly enabled in `game.tscn`, but the
underlying setting still has a `false` default. Deleting both branches and
removing `GamebryoTerrainBuilder` makes Terrain3D mandatory; that can be a
valid decision, but it is a behaviour/configuration migration, not simply an
ownership extraction with zero change.

State the decision explicitly: Terrain3D is now the sole supported exterior
terrain path, the fallback is intentionally deleted, and the old toggle is
removed. Then add a smoke/regression test for initial exterior load and an
exterior-to-interior-to-exterior return. If compatibility fallback is desired,
do not delete it in Phase 1.

### 4. Phase 3 queue ordering is underspecified and the wording is false

The queue does not “only drain forward” when its distance priority centre
moves. A min-heap ordered around the old player coordinate is immediately
wrong after the player travels, and blindly adding priority requests creates
duplicates and starvation. Specify:

- the authoritative coordinate source (TerrainStreamer’s camera, not a
  private `WorldStreamer._current_grid_coord()`);
- a per-cell state machine (`unseen`, `queued`, `preparing`, `prepared`,
  `committed`, `cancelled`) keyed by worldspace + coordinate;
- how priorities are recomputed/rebuilt when the centre moves materially;
- duplicate suppression and how explicit WorldStreamer priority requests
  interact with the ordinary near/far budgets; and
- a fairness rule so the low-priority world fill eventually progresses.

Without this, “one queue, one ordering rule” is only a slogan.

### 5. Keep the worker boundary hard; do not make an unsafe experiment a gate

The plan now chooses the correct architecture: workers produce detached value
data and the main thread commits it. In that design a “dedicated
thread-safety test” must not be read as future permission to mutate live
`Image`, `Terrain3DRegion`, `Terrain3DData`, resources, or the renderer from a
worker. There is no need to prove that broader claim because it is outside the
design.

Replace the gate with a detached-payload test/benchmark: private-reader LAND
preparation runs in parallel, returns only owned plain data, cancellation drops
the result by generation, and every Terrain3D/Resource call is asserted on the
main thread. Name the payload ownership/lifetime and the per-worker reader
context explicitly; “same pattern as placement resolve” is not enough when
the task can outlive a worldspace transition.

## Important corrections and missing work

### Texture memory claim needs evidence, not an overcorrection

The plan correctly rejects one `Terrain3DTexturePool` for multiple terrain
instances. It then says texture data is necessarily a per-worldspace cost
under either proposed design. That does not follow. Each Terrain3D needs its
own `Terrain3DTextureAsset` slot table and material binding, but the decoded
`Texture2D`/GPU image may still be shareable through `GamebryoMeshResolver`’s
resource cache when the same DDS is used by two worlds. Measure and report
separately: per-Terrain3D asset/array bookkeeping, decoded image resources,
and GPU texture allocation. Do not promise either sharing or duplication until
that is observed.

### Lifecycle is split across phases without a clean boundary

Phase 1 must already own the single-active-world exterior ↔ interior
pause/resume path, including visibility, collision, processing, camera binding
and readiness invalidation. Phase 4 should extend that proven lifecycle to a
multi-world registry, not introduce the first real lifecycle implementation.
For inactive cached worlds, explicitly establish that their Terrain3D nodes do
not continue processing or clipmap/collision work just because they are hidden.

### Deterministic edge policy must be selected before parallel commits

The plan identifies the shared-border problem but defers its solution as an
either/or. Pick one before Phase 2 starts. A canonical owner for each shared
vertex/map sample is simpler to reason about than completion order. The policy
must cover height, normals, colour, both texture-ID maps, and both weight maps;
the regression should compare completed terrain under deliberately varied task
completion order.

### Diagnostics are part of the ownership move

`world_streaming_debug_tab.gd` currently reads
`Game/WorldStreamer._terrain3d_pool` directly. The planned extraction will
break it. Move texture-pool and terrain queue status to TerrainStreamer (or a
dedicated terrain debug tab) as part of Phase 1, rather than leaving a stale
private-field dependency. Include the scene/UI references in the change list.

### Phase 0 should settle actual operational bounds

The census/benchmark list is much better. Add explicit deliverables for:

- Terrain3D’s usable region-coordinate bounds versus every surveyed
  worldspace, including the required coordinate transform;
- measured clipmap horizon at the real mesh settings, compared with observed
  vanilla terrain visibility rather than only a cited configuration value;
- collision coverage and update behaviour after region commits; and
- a reproducible benchmark scene/script and hardware/settings record, so later
  throughput numbers are comparable.

## Acceptance criteria to add

Before calling the plan complete, require all of the following:

1. Game transition code consumes a single generation-safe terrain readiness
   API, including a transition that is cancelled/replaced mid-wait.
2. `WorldStreamer` has no Terrain3D field, bridge call, grass call, or direct
   debug/UI dependency; it can only submit the documented priority request.
3. Worker results cannot mutate any Godot resource and stale results cannot
   commit after pause/deactivate/world switch.
4. Queue state/ordering is deterministic under duplicate requests and a moving
   player, with a test demonstrating both near responsiveness and eventual
   background progress.
5. Terrain texture allocation/sharing is measured across two resident
   worldspaces; do not infer it from the pool object graph.
6. The live debug UI remains functional after the ownership extraction.

## Bottom line

Approve Phase 0 research after the plan is amended to make the topology,
readiness API, and queue state machine explicit. Do **not** start the
TerrainStreamer extraction or thread work until those contracts are written.
The rendering direction is now sound; the remaining defects are implementation
coordination defects, and they will be expensive to unwind if they are left as
implicit assumptions.
