Terrain Streaming Plan

A working plan for issue #19: pull exterior terrain ownership out of cell streaming entirely and give it a dedicated Terrain3D-only pipeline with a third, broad-distance residency tier — so the Mojave's distant mountains render the way they do in the original game.

Target: github.com/Lewin225/GodotBryo #19 Touches: world_streamer.gd, terrain3d_bridge.gd, terrain3d_texture_pool.gd Status: pre-implementation — Phase 0 not started
PHASE 0

Research & audit

The issue's own deliverable requires this to land as a comment before any code — real coverage figures, Terrain3D's real constraints, and a migration plan grounded in both, not assumption.

Worldspace coverage survey

  • Extend native/tools/terrain_census (already exists, built for exactly this kind of question) to report per-worldspace LAND record count, grid bounding box, and gaps within that box, for WastelandNV and every other terrain-owning worldspace (Freeside, at minimum).
  • Cross-check against the region-count ceiling already discovered the hard way in terrain3d_bridge.gd: Terrain3DData's region map is a fixed 32×32 grid, which is why region_size was raised from 128 to 256. Confirm 256 still holds once a distant tier pushes real region residency further from center than any full-detail tile ever has.
  • Measure real per-region memory (height + control + normal maps at region_size=256) so a "keep every worldspace resident, never evict" policy (per the issue's own Phase-3 scope) has an actual number behind it, not a guess.

Vanilla behavior

Confirmed by web research

FNV's own Gamebryo terrain LOD is a real, documented LOD4 / LOD8 / LOD16 / LOD32 hierarchy — pre-baked simplified meshes (Meshes\Landscape\LOD\<Worldspace>\*.NIF) plus baked diffuse/normal textures, grouped by cell-block size (4×4 up to 32×32 cells), all generated offline. This is the same "reuse Bethesda's own pre-baked LOD data" approach the project already took for object LOD (phase 2.12, _lod.nif pairs) — ROADMAP.md's Phase 2 bullet names it explicitly: "FNV ships pre-baked LOD meshes and distant land data — reuse them rather than generating LOD at runtime."

Open question

Issue #19 already commits to a different approach — feeding Terrain3D's own clipmap LOD with continuously-streamed real LAND heightmap data, not reusing Bethesda's pre-baked terrain LOD meshes/textures the way 2.12 did for objects. That's a deliberate fork from this project's stated default (reuse pre-baked data), not an oversight — worth a one-line confirmation that it's still the intended direction before Phase 2 builds on it, since the pre-baked LOD meshes are sitting right there as a lower-effort alternative for the broad tier.

  • Direct observation still matters for one thing the LOD files alone don't answer: how far out the pre-baked LOD tiers are actually visible in real play before atmospheric fade/sky dome hides them — that's the real target radius for whatever tier ends up rendering it.

Terrain3D capability check

  • Read native/terrain3d/src/terrain_3d_region.h / terrain_3d_collision.cpp directly (the project's own established convention — set_paused()'s collision-mode comment in world_streamer.gd already did this rather than assuming) to determine whether collision and grass can be scoped per region, or only globally the way set_collision_mode() is called on the whole Terrain3D node today.
Reconsidered, twice

Originally scoped this as "determine whether distant regions need full texture blending or can skip it." First pushback: prewarm_textures() pays that cost up front, so painting distant cells looked free. Second pushback corrects that: prewarm_terrain_textures (still true by default, world_streamer.gd:155) exists only to work around a shader-regeneration corruption bug in the addon's own texture-add path (see its own doc comment) — that bug is long fixed, and real testing has been running with prewarm disabled for a while now, at the cost of a noticeably slower first paint on the exterior world as textures resolve lazily instead.

So the real picture: without prewarm, resolving a texture the first time it's seen (normalize, slot assignment, upload) is a genuine per-texture cost — but it's the exact same cost nearby cell streaming already pays today, not something the broad tier introduces. Phase 2's continuous outward fill just meets that cost progressively as it expands into new territory, the same way ordinary streaming already does. Working assumption stays the same either way — one import path, no reduced-fidelity distant variant — but the "why it's fine" reasoning changes from "already paid" to "same cost that already exists, just spread out." Worth adding as a real Phase 0 task: measure lazy per-texture resolve cost under the continuous fill's pacing, and decide whether prewarm_terrain_textures's default should flip to false now that its original bug justification no longer applies.

Main-thread boundary audit

Read native/terrain3d/src/terrain_3d_data.cpp directly rather than assuming — the real boundary turns out to be narrower than import_cell()'s current all-synchronous shape suggests:

Confirmed from source

Terrain3DData::set_pixel() (terrain_3d_data.cpp:749), which set_height() is a thin wrapper over, is just Image::set_pixelv() on the region's own CPU-side Image plus a set_modified(true) flag — no RenderingServer call, no signal, nothing GPU-facing. The 33×33 per-vertex loop that dominates import_cell()'s cost is, on its own, genuinely worker-safe. Three things around it are not, confirmed from the same read:

Region creation — ensure_regions_for_cell() → add_region_blank() mutates terrain.data.region_locations directly, and a brand-new region growing the GPU texture arrays needs the full update_maps() rebuild. First-time texture resolution — Terrain3DTexturePool.get_slot() creates/normalizes a real Texture2D the first time an LTEX is seen, the same restriction GamebryoMeshResolver's existing raw-resolve/main-thread-build split already enforces for meshes. Post-loop bookkeeping — update_maps()/calc_height_range()/ set_edited() explicitly regenerate the GPU texture arrays and emit *_changed signals.

  • The natural split mirrors the existing object-placement shape (resolve_tile() / construct_from_resolved()): a worker task does the ESM read (per-worker EsmReader, same GamebryoResolveContext pattern), decompression, and every per-vertex height/normal/color/N=7-weight computation — pure data, no Terrain3D touch. A narrow main-thread commit then ensures the target region(s) exist, resolves any genuinely-new textures, writes the prepared arrays via set_pixel(), and runs the post-loop rebuild.
  • Real hazard to design around, not incidental: two adjacent cells can share a boundary region — import_cell()'s own header comment already documents this for odd grid coordinates. Concurrent workers must not write into the same region unsynchronized; needs a per-region claim before dispatch (region-level exclusivity, not just per-cell), not a blanket "any cell on any worker" assumption.
  • Still worth confirming with real profiling once built: how much of import_cell()'s current cost is actually the worker-safe loop versus the three main-thread-only pieces — that ratio determines whether the split is worth its own complexity, or whether decoupling from WorldStreamer's bursty per-tile calls (Phase 1/2) already removes most of the felt stall on its own.
Exit signal — a GitHub comment on #19 with real coverage numbers, the pre-baked-vs-live-LAND confirmation, the region/collision capability findings, and the measured worker-safe/main-thread cost split above — before any of Phase 1 starts.
PHASE 1

Extract terrain into its own owner

One exterior-terrain owner, full stop. WorldStreamer stops importing terrain in any form; cell streaming becomes REFR/collision/interactive-object content only.

New class: TerrainStreamer

  • Owns the shared Terrain3D node, Terrain3DTexturePool, Terrain3DBridge, and TerrainGrassParticles — all four currently live as WorldStreamer member fields (_terrain3d, _terrain3d_pool, _terrain3d_bridge, _terrain_grass_particles), created in activate() and freed in deactivate(). Those four fields move out wholesale.
  • Gets its own residency dictionary, load queue, and per-frame throttle, structured the same way WorldStreamer's own _resident/_queued/_load_queue/tiles_per_frame already work — proven shape, not a new one to invent.
  • Gets its own diagnostics, mirroring the existing diagnostic_terrain_ms array and the opt-in freeze_trace_enabled pattern from issue #6 — a second independently-observable trace, not folded into WorldStreamer's.
Confirmed from source

prewarm_regions(wrld_form_id) — a sibling to the existing prewarm_textures() — batch-registers every region for the worldspace's known extent (Phase 0's coverage survey) at activate(), once, before any real cell import happens. Traced why this is a real win, not just plausible: GeneratedTexture:: create() (generated_texture.cpp:26) is a full RS->texture_2d_layered_create() — discards the old array RID and re-uploads every resident region's image, the real O(total-resident-regions) cost. GeneratedTexture::update() is a cheap per-layer RS->texture_2d_update(). add_region_blank(loc, p_update=false) — what ensure_regions_for_cell() already calls — registers a region without triggering the dirty flag that forces .create(); it's specifically import_cell()'s own if created_new_regions: terrain.data.update_maps() (default args) that pays it, once per cell that happens to expand into new territory. Batch-register everything, then one explicit update_maps() call while the worldspace is still empty, and created_new_regions is never true again for the rest of the session — every real import takes the cheap incremental path unconditionally.

Real cost, not free: a blank region's default height fill is COLOR_BLACK → 0.0 (terrain_3d_region.h:53), so pre-registering the whole worldspace up front means it renders as a flat sea-level plane out to the world edge immediately, before real LAND data overwrites it.

Deprioritized per feedback — a real post-implementation issue, not a blocker for this plan. Three candidate mitigations to pick between later, once prewarm_regions() is actually being built (see the upstream-context callout below for whether it's needed at all): gate the load screen until the region is genuinely ready (ties into the readiness- contract note above), a scaling fog effect to hide the seam, or caching terrain data across sessions so this becomes a one-time boot cost instead of a per-worldspace-switch one.

Upstream context — decided

Terrain3D#381 (closed, milestone 0.9) is where the cheap per-layer .update() path above actually came from — its own discussion thread proposed almost exactly the prewarm_regions() workaround above ("preemptively allocate a larger array... shrink it during idle time") back when this was filed, but it was never generalized into a shipped fix.

Terrain3D#1004 (draft, milestone 1.2, unmerged) solves the underlying problem properly instead: a fixed-capacity slot pool that decouples region_id from the texture-array layer/position entirely, so add/evict touch exactly one layer + one region-map entry, arrays allocated once. No world-size-upfront knowledge needed, and no flat-plane artifact — regions genuinely don't exist until streamed in (real threaded disk loads, real eviction). The PR explicitly names this project's exact problem as a planned upstream feature: "some kind of far-field hook so the horizon doesn't pop where regions end... probably fits upstream better." It also bundles an isolated, independently real fix — Terrain3DMaterial::update() was testing p_flags & FULL_REBUILD, which matches every non-zero flag since FULL_REBUILD is a superset mask, forcing a full shader recompile on every single maps_changed — their worst churn-test frame went from ~900ms to ~17ms fixing just that. import_cell() already fires maps_changed on every cell today; worth checking whether this project is silently paying that cost right now, independent of anything else in this plan.

It's draft, 1.2-milestone, Linux-only tested, and touches the exact region/texture-array machinery this project has already heavily patched for the real N=7 blend format — adopting it wholesale now risks a real conflict with those local patches. Decided, per feedback: port the isolated FULL_REBUILD shader-flag fix now (small, real, unrelated to streaming) — then track #1004 toward eventual adoption/rebase once it's closer to merged upstream, rather than reinventing slot-pooling independently — and only build prewarm_regions() above as a stopgap if this implementation turns out to still have real perf issues once it's actually running, not preemptively.

WorldStreamer changes

  • Delete the entire use_terrain3d branch inside _stream_tile() — both sides. Resolved per feedback: the legacy, non-Terrain3D GamebryoTerrainBuilder mesh path is deprecated and can be removed outright, not preserved as a parallel system. TerrainStreamer becomes the only terrain path; use_terrain3d, terrain_root, and CellStreamBuilder.build_terrain()'s call site all go away with it.
  • Cell streaming may request priority for the coord it's about to populate — a plain method call into TerrainStreamer, not an import — but never touches Terrain3D itself.
Added, per feedback

WorldStreamer and TerrainStreamer need an aligned readiness contract for dismissing the load screen / unpausing the player, not two independent "settled" notions. Today, WorldStreamer.streaming_settled alone gates game.gd's _do_exterior_transition() await — once terrain ownership moves out, that signal only reflects object/REFR residency near the player, not whether nearby terrain has actually imported. The priority-request call above needs a matching readiness signal (e.g. TerrainStreamer reporting settled once the requested coord's own region data has landed), and the transition await needs to wait on both — otherwise the player can be released standing over terrain that hasn't streamed in yet.

PHASE 2

Continuous outward terrain fill

Rejected per feedback: no second radius tier, no reduced-fidelity import path. Instead, TerrainStreamer fills outward from the player continuously until there is no worldspace left to import, at two speeds rather than two data profiles.

Direction, per feedback

"No more radius tiers in TerrainStreamer. Start where the player is and import cells till there's none left to import. Cells past the LOD2 radius (WorldStreamer) can be loaded at a less demanding speed." Combined with the Phase 0 texture-cost finding above, this collapses to one import path (import_cell(), unchanged — full height + N=7 texture blend every time), driven by one outward-expanding priority queue instead of a bounded radius check.

  • TerrainStreamer tracks the same grid-coordinate center WorldStreamer already derives (_current_grid_coord()) and maintains a priority queue ordered by distance from it — nearest unimported cell first, no upper bound. A tile leaving the resident set doesn't need re-deriving each check the way WorldStreamer's hysteresis bands do, since nothing here ever unloads (Phase 3): the queue only ever drains forward.
  • Two throttle rates instead of two tiers: cells within WorldStreamer.RADIUS_LOAD_DISTANT (today's "LOD2", 20 grid cells) import at the existing responsive pace; cells beyond it import at a deliberately slower cadence — fewer tiles_per_frame-equivalent starts per tick, same import path, so there's no second code path to keep correct, just a different budget.
  • WorldStreamer's existing priority request (Phase 1) bumps a coord to the front of this same queue rather than triggering a separate fast-path import — one queue, one ordering rule, not two systems racing.
  • Investigate the issue's own suggestion: resolve LAND directly by grid coordinate/FormID rather than going through find_exterior_cell() → full CELL resolution, since the outward fill will eventually touch every coordinate in the worldspace including the many that never need REFR/CELL data at all. The 2.11 exterior-cell lookup index fixed the general find_exterior_cell() cost (81% of tile-streaming settle time before that fix) — confirm whether that index (or a narrower LAND-only variant) serves this without pulling in CELL/REFR data the terrain fill doesn't need.
  • "Until there's none left to import" needs a real termination check per worldspace — the same missing-cell/gap survey from Phase 0 doubles as the stop condition, and reuses WorldStreamer's own _no_cell_cache pattern for coordinates confirmed to have no real LAND.

PHASE 3

Per-worldspace terrain lifetime

Terrain residency belongs to a worldspace, not a reusable buffer. Switching from WastelandNV into Freeside must hide, not overwrite, WastelandNV's terrain.

Confirmed, per feedback

"Build and keep warm a terrain3d for each encountered worldspace. They all share the same texture pool, so it's just heightmap data. Memory usage can be tweaked or optimised down the road." Corrects an assumption in the original draft: Terrain3DTexturePool is one shared instance for the whole session, not duplicated per worldspace — it already holds every real ground texture across the map (prewarm_textures(), ~64 total). Only the heightmap/region data (Terrain3D node itself) is genuinely per-worldspace.

  • Replace WorldStreamer.deactivate()'s current behavior — _terrain3d.free(), unconditionally, on every worldspace switch (world_streamer.gd:304-311) — with a per-worldspace registry inside TerrainStreamer holding only { wrld_form_id: { terrain, bridge, grass, resident } }. Terrain3DTexturePool stays a single field on TerrainStreamer itself, created once, shared across every entry.
  • A worldspace switch hides the outgoing entry (reusing the exact pattern set_paused() already established: visible = false plus Terrain3D.set_collision_mode(DISABLED) — both already known to be necessary, not just node visibility) and activates or creates the incoming one.
  • Returning to a previously-loaded worldspace reactivates its retained instance rather than rebuilding — no re-import needed, and since the texture pool was never worldspace-scoped in the first place, there's nothing to re-warm on the round trip either.
  • No eviction, no memory-pressure policy — explicitly deferred, tweakable later once real per-worldspace heightmap memory numbers exist (Phase 0).
Exit signal — Goodsprings → Freeside → Goodsprings round trip: WastelandNV terrain reappears instantly on return, no re-import, no cross-contaminated region data from Freeside.
